# Subagent Dispatch Protocol

这个协议用于 `xman-flow` 在需要子代理执行某个阶段时，保证子代理真正加载对应阶段 skill，并将结果稳定回流主流程。

## 适用场景

只有在以下场景之一出现时，才应派发子代理：

- 当前阶段工作量较大，适合独立上下文执行
- 当前阶段可以与主流程的其他工作并行推进
- 当前阶段需要隔离上下文，避免污染主线程判断
- 当前阶段更适合由专门的执行者完成，而主流程继续负责编排

如果当前阶段很短、依赖强上下文连续性，或无法从主流程中拆分，就不要为了用子代理而用子代理。

## 派发前检查

按 `.ai-configs/conventions.md`〈阶段职责与证据复用〉核对待解决问题、既有产物和证据。没有独有未决问题时复用，不重复派发；确需派发时填全下方输入，并按 `./shared-artifact.md`确定最终写入者和当前执行者负责的内容。

## 派发原则

1. 子代理只负责单一阶段，不负责接管整个流程
2. 子代理必须显式读取对应阶段 skill 的 `SKILL.md`
3. 子代理必须基于主流程传入的输入执行，不能自行改写任务边界
4. 子代理完成后必须返回结构化结果，便于主流程继续决策
5. `xman-flow` 必须保留流程控制权、状态记录权和最终汇总权

6. **审查默认继承当前模型。** 使用独立上下文和可复核证据评判产出，不把实施者的
   解释当成结论。用户明确要求或有实际对比需要时才换模型，不为审查增加固定模型路由。

## 标准派发模板

下方 `./` 路径相对于本文件所在目录。派发前将它们解析为当前安装位置的绝对路径，填入给子代理的消息；不要按业务项目根目录解析。

```text
你是当前任务中被派发来执行单一阶段的子代理。不要接管整个流程，只完成当前阶段。

开工前先用 Read 工具读取以下阶段 skill 和伴随文档，并按完整协议执行：
- 当前阶段 skill：`../../../skills/<mapped-skill>/SKILL.md`
- 阶段唤醒模板：`./stage-wakeup-template.md`
- 子代理派发协议：`./subagent-dispatch-protocol.md`
- 如果不知道仓库根目录，先用 Glob 搜索：
  - `**/skills/<mapped-skill>/SKILL.md`

当前阶段信息：
- 阶段：<stage>
- 默认 skill：<mapped-skill>
- 待解决问题：<本阶段独有、尚未解决的问题>
- 用户需求：<user-request>
- 已授权范围与已确认决定：<authorized-scope>
- 已确认结论与产物或记录条目：<上一阶段及相关决定的位置>
- 未决事项：<建议、假设、待核验或待裁决项及影响>
- 可复用证据：<已有检查记录及覆盖范围>
- 本阶段独有产出：<新增判断或内容；文件交付写产物路径>
- 输出所有者与负责内容：<最终写入者、当前执行者负责的文件或章节>
- 额外约束：<constraints>

执行要求：
- 先读取对应阶段 skill 的 `SKILL.md`
- 同时遵守阶段唤醒模板和子代理派发协议中的边界要求
- 按该 skill 的完整协议完成当前阶段
- 不要越过当前阶段直接处理下一阶段
- 按 conventions 的阶段证据规则与共享产物写入责任执行；你不是独自工作，不回退他人的改动
- 输入不足时先查证；局部可逆细节按代码与验证决定并记录理由，真实业务或契约选择返回主流程，只阻塞依赖项，不擅自扩展任务边界

按下方格式返回当前阶段结果。
```

## 返回结果格式

子代理返回结果必须尽量贴近以下结构：

```text
[阶段结果开始]
阶段：<stage>
结论：<summary>
根本原因或关键依据：<evidence>
产物或章节稿或记录条目：<文件路径或负责章节内容>
已确认部分：<有依据的事实及已确认决定，允许为空>
验证结果：<新运行、复用证据与覆盖范围，或说明未验证>
下一动作：<next-step>
风险与未决项：
- <风险的实际名称、影响和处理状态>
- <未决问题的实际名称、所需证据和下一动作>
[阶段结果结束]
```

## 主流程回收规则

子代理返回后，`xman-flow` 主流程必须：

1. 校验子代理是否真的执行了当前阶段，而不是越界处理其他阶段
2. 核对独有问题的结论、依据、产物或章节稿及证据覆盖；共享最终稿由指定所有者合并，风险与未决项存在时必须返回
3. 将返回结果纳入当前流程状态；逻辑完成和记录完成分别核对，对话交付按 agent 定义〈对话交付的阶段记录〉保存到现有 journal/progress，不强造独立报告
4. 判断下一步是继续、补充、重试还是回退前置阶段；完成审查或分析不代表建议获批，下游只依赖已确认部分。用户只要求单阶段时在该范围结束
5. 由主流程统一向用户汇报，不把流程控制权交给子代理
6. **回收待确认项**：先区分可查证事实、局部实现细节和必须由用户裁决的选择。前两类由主流程补证据或重派处理；真实业务或契约选择整理成一组问题，答复后更新前序产物并重派依赖任务。等待期间继续无依赖工作，不能因为无人应答就默认改变业务或契约

## 失败判定

以下任一情况视为子代理派发失败：

- 没有要求子代理先读取对应阶段 skill 的 `SKILL.md`
- 子代理结果无法证明其只处理了当前阶段
- 子代理没有返回结构化结果
- 子代理擅自接管后续阶段
- 主流程没有回收结果就继续往下走
- 子代理自行决定了本该由人拍板的缺口，而不是记成待确认项返回

## 设计原则

- 子代理是阶段执行器，不是总控
- 主流程是编排者，不是旁观者
- 派发是为了降低复杂度，不是为了逃避主流程责任

## Prompt 模板引用

针对常见的子代理派发场景，已提供预制的 Prompt 模板。使用模板可以确保子代理获得足够的上下文和约束。

| 场景 | 模板文件 | 何时使用 |
|------|---------|---------|
| implement 阶段编码 | `./implementer-prompt.md` | 派发子代理执行编码实施时 |
| review 阶段审查 | `./reviewer-prompt.md` | 派发子代理执行代码审查时（规格合规 + 代码质量一次跑完，单子代理） |

**使用规则：**
1. 优先使用预制模板，而非从零构造 prompt
2. 模板中的 `{变量}` 必须替换为实际值
3. 模板变量替换必须是纯文本替换，不依赖三元表达式、脚本执行或额外模板引擎
4. 可以在模板基础上追加项目特定的约束
5. 不得删减模板中的必读文件和状态返回协议
