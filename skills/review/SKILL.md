# 代码审查

找出本来可能遗漏、会造成明确业务后果的缺陷，按失败代价排序。「后果」指业务后果：死代码、注释和实现对不上、契约没写，这些只是线索。顺着线索问三句：**谁会卡住？卡住后能自己出来吗？有人会知道吗？** 答不出来，它还不是发现。

每条发现都给出代码位置、触发条件、影响和证据；证据不足就继续验证，或放进「待验证」。四条底线：

1. **类比不进结论。**「这像 N+1」是待验证的假设，要么去验证，要么放进「待验证」。
2. **先建立独立理解，再看规格。** 变更审查先读 diff 再读 PRD 和计划：实现常常是同一个 agent 写的，先读验收标准等于先抄答案。模块审查里契约是证据源（「契约要求 X，代码没做」本身就是发现），但同样先建立代码侧的理解。
3. **运行期结论要有覆盖当前对象的运行证据。** 复用结果注明来源和覆盖范围；没有就标为推断。
4. **注释、测试 docstring 和文档记录的是当时的意图。** 拿它们替现状辩护前，先核对它描述的场景和眼前的是不是同一件事。一条测试守着某个行为，只说明有人写过它。

证据复用按 `.ai-configs/conventions.md`〈阶段职责与证据复用〉；方法细节在 `references/evidence.md`，每次审查都读。

## 选模式

先看用户话里的审查对象：

| 审查对象 | 模式 |
|---|---|
| diff、commit、PR、本次改动、刚改的、暂存区、某个分支区间；什么都没说 | 变更审查 |
| 模块、系统、链路、流程、「整个 X」；点名并发、幂等、状态流转、越权、重试、事务边界；只给了目录或模块名 | 模块深度审查 |

- 点名了模块，同时工作区有未提交改动：仍是模块深度审查，用户点的对象优先。
- 「这次改动有没有并发问题」：变更审查，只是收窄到并发这一类。范围词优先于风险词。
- 什么都没说而 `git diff` 为空：先确认要审最近一次提交还是某个分支区间，确认不了就问，范围保持不变。
- 变更审查做到一半发现根因在模块层：照常出变更审查结论，另起一段建议单独做一次模块深度审查。

两种理解会给出不同结论时，问一句：审这次改动，还是审整个模块。

报告第一行写模式，用户一眼就能纠正：

```text
🔍 代码审查 · 变更审查 · 标准
🔍 代码审查 · 模块深度审查 · services/compliance
```

## 变更审查

1. **固定审查对象。** 用户给了提交、分支或区间时，用 `git rev-parse --verify '<ref>^{commit}'` 核实端点并记下解析后的提交，以及用两端差异还是 merge-base 差异；后续读取都沿用这两个提交。命令失败是读取失败，不当成空 diff。未提交改动则记下工作区和暂存区范围。
2. **选深度。** 行数决定工作量，风险决定深度：

   | 深度 | 触发 | 输出 |
   |---|---|---|
   | 快检 | < 50 行或单文件 | 排序后的问题 + 一句判定，不落文件 |
   | 标准 | 50–300 行；或命中下面任一风险，不论行数 | 快检 + 需求对照 + 测试缺口 |
   | 详细 | > 300 行，或用户要汇报 | 标准 + 值得保留 / 未决项 / 下一步 |

   风险项：鉴权与权限、租户或用户隔离、金额余额库存、状态流转字段、任何 `INSERT` / `UPDATE` / `DELETE`、事务与锁、幂等、消息队列与定时任务、数据库迁移、支付与第三方调用。超过 500 行且跨多个模块时，先建议拆分；用户坚持就按相关改动分组，并说明没覆盖的范围。
3. **只读 diff 建观测表。** 这一步只看 diff，PRD、计划和项目上下文留到下一步。逐条记观测，不写解释，例如「`auth/login.go:42-58` 新增 for 循环，最多 3 次调用 `login()`」，而不是「实现了登录重试」。做法见 `references/change-review.md`。
4. **核对已有证据，补跑自动检查。** 用项目自己的 typecheck、lint、test、build 命令（从 `Makefile`、`package.json`、CI 配置里读），只补跑缺口或失效的部分；脚本变更时跑 `shellcheck`。什么都没跑成就在报告里写「未运行任何验证」。
5. **分两条线审查。** 两条线回答不同的问题，一条通过不代表另一条通过：

   - **需求**：做没做对。按 `.ai-configs/conventions.md` 的产物路径找计划、PRD 或需求分析，取出验收标准，逐条判定通过 / 部分通过 / 未通过，附证据位置；同时找计划外的改动，判断是否为完成目标所必需。没有正式标准就从 commit message 和观测表推断预期，并注明「无正式验收标准」。规格缺口不阻断本轮，报告里排最前。
   - **缺陷与规范**：做得稳不稳。按 `references/change-review.md` 的通用骨架查契约变更、错误路径和影响范围，按下表加载风险文件；按项目规范和 skill 安装目录里的 `create-plan/references/engineering-checks.md` 核对规则归属与依赖。建好观测表之后，调用 Skill 工具（参数为 `spec-query`），用实际变更路径读取命中的规范；索引非法或匹配不确定时写「Spec 未完成对账」。有结构线索时读 `references/design-smells.md`，异味只用来提出可验证的问题；涉及接口深浅、复杂度归属或替换点时，用 skill 安装目录里 `create-plan/references/module-design.md` 的术语和 deletion test。

   宿主支持子代理时，两条线各派一个子代理并行，互不污染上下文：每个子代理拿到固定的 diff 命令、观测表和本条线需要的材料，报告不超过 400 字。不支持时按「缺陷与规范」「需求」的顺序依次做。汇总时两条线分开呈现，不合并、不跨线重新排序。
6. **用三问过滤每个候选问题**（见下文）。

| 触发信号 | 加载 |
|---|---|
| 样式、组件文件、前端依赖、发请求的组件 | `references/risk-frontend.md` |
| SQL / ORM、事务、锁、并发原语、消息队列、定时任务、接口 handler、迁移、状态字段 | `references/risk-backend.md` |
| 脚本、Makefile、Dockerfile、CI、部署、子进程、配置与环境变量 | `references/risk-ops.md` |

命中几个加载几个；一个都没命中时，通用骨架就是全部。

## 模块深度审查

读 `references/module-review.md`，按其中方法做。找问题之前必须先交出两样东西：

1. **运行形态**：进程与线程模型、有没有跨进程锁、数据库隔离级别、定时任务和消费者是否独立进程、客户端重试策略。不确定这些，并发结论都无法证伪。
2. **写入口清单**：枚举所有产生副作用的入口，逐条追到 SQL，记下写什么、并发保护和幂等保护。只跟着有副作用的链路走，不逐文件通读。

然后拿契约对账：逐条问「契约要求的约束落在代码哪一行」。沿链路查幂等身份是否跨层混用、状态机与业务不变量、权限的资源归属和角色两个维度、失败与恢复。

## 三问过滤

每条候选问题报出前过一遍：

1. **影响面对得上吗？** 这条成立的话，相邻调用点和同模式代码也该受影响。grep 过了吗？
2. **既有代码为什么能正常运行？** 解释不了就降级或删掉。模块审查里尤其要查清是哪一层兜住了，这决定它是「会丢数据」还是「会退化成一个 500」。
3. **边界说得出来吗？** 什么输入、什么条件下不发生？

三问过不去的不进结论。见到 `SELECT → 判断 → INSERT` 这类并发形状，先查唯一约束、行锁、乐观锁、条件 UPDATE 和调用方串行，都没有才定为问题。

## 输出

每条问题带证据等级：**事实**（亲眼读到或亲手跑到，附位置或命令输出）、**推断**（用人话写清推导链）、**类比**（只能进「待验证」，不带严重度）。

```text
[推断] 必须修复 · internal/cache/key.go:88
并发批量调用时 cache key 会碰撞
推导：key 只用了 userID，而这个方法在按租户并发的 worker 池里调用，
     同一用户跨租户的请求会共用同一条缓存
影响：串租户读到彼此的数据
建议：key 补上 tenantID
```

- **影响**写谁受损、能不能自己恢复、有没有人发现，而不是代码处于什么状态。
- **建议**先说这条业务路径应该怎么走通，再说代码怎么改；把几个选项原样丢回给作者不算建议。
- 贴日志、抓包、配置或命令输出前先脱敏：密钥、token、连接串、内网地址、真实用户标识换成 `<REDACTED>`，只引用携带信号的那几行。

变更审查报告：

```text
🔍 代码审查 · 变更审查 · [快检 / 标准 / 详细]

判定：[✅ 可合并 / ⚠️ 需修复后合并 / ❌ 需重做]
验证：[新运行 / 复用结果与覆盖 / 或「未运行任何验证」]

## 需求
规格缺口和计划外改动，逐条附证据

## 缺陷与规范
按失败代价排序，单条格式见上

待验证：[类比] 描述 —— 验证方式与成本
测试缺口：……

两条线各自的问题数，以及各自最严重的一条
```

- 空的分组整段不出现。快检可以不分两条线，直接给排序后的问题和判定。
- 每条线每个严重度最多 5 条，超了就合并同类或降级。
- 判定：没有必须修复的问题是「可合并」；有但能局部修正是「需修复后合并」；实现方向和验收标准不符，或必须修复的问题遍布主路径是「需重做」。判定反映事实，宁可 ⚠️ 也不给假绿灯。
- 快检和标准审查直接在对话输出。详细审查在用户要求留档或当前任务已有 review 路径时，按 `.ai-configs/conventions.md` 保存，模板见 `assets/templates/review-report-template.md`。

模块深度审查报告：第一行模式，然后是运行形态、验证情况、按代价排序的问题清单（不设上限，每条加触发条件和是否有数据库兜底）、3–5 条从多条发现归纳出的系统性风险，以及必出的「明确没发现问题的部分」（查了什么、怎么查的、为什么判定干净）。不出合并判定，默认落文件。格式见 `references/module-review.md`。

## 可以放宽规则的情况

1. 用户只要某一类发现（「只看安全」）：按要求收窄，其余规则保留。
2. 前方有破坏性变更（schema 迁移、删数据、force push）：哪怕只是推断也先说。
3. 用户已经知道某个问题并说「先不管」：不再重复列，也不因此改判定。
4. 紧急故障排查中：直接给最可能造成严重后果的问题，格式事后补齐。
