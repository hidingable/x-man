# 变更审查细则

主文件规定流程，这里是变更审查里「建观测表」和「缺陷与规范」这条线的具体做法。

## 只读 diff 建观测表

用 `git diff` / `git diff --cached` / `git show HEAD` 拿到变更。PRD、编码计划和 project-context 留到观测表建完再读。

逐条记录**观测**，不写**解释**：

| ❌ 解释 | ✅ 观测 |
|---|---|
| "实现了登录重试" | `auth/login.go:42-58` 新增 for 循环，最多 3 次调用 `login()`，间隔 1s |
| "重构了表格组件" | `Table.tsx` 拆成 `Table.tsx` + `useTableData.ts`，导出签名未变 |
| "修了那个缓存 bug" | `cache.py:20` 的 key 从 `user_id` 改为 `f"{user_id}:{tenant_id}"` |
| "加固了部署脚本" | `deploy.sh:1` 新增 `set -euo pipefail`，第 14 行 `$TARGET` 加了引号 |

每行带：变更内容 / 位置 / 类型（新增 · 修改 · 删除 · 移动）/ 对外契约是否变化。

观测表建完，才允许往下读需求文档。

## 缺陷与规范：通用骨架、结构信号与重构

### 通用骨架（任何代码都查）

1. **契约变更** — 导出签名 / 返回结构 / 配置项 / DB schema 变了吗？调用方跟上了吗？
2. **错误路径** — 失败分支、空值、超时、重试，写了吗、写对了吗？
3. **影响范围** — 对被改动的符号 grep 引用者，逐个确认没被打破。

### 结构信号：三条可指认的事实

下面三条出现时，问题不在这一行代码，而在它所处的结构。它们是**能指出位置的事实**，不是「感觉该重构」：

1. **同一个绕法出现在互不相关的调用点** — 不是同一个模块里重复，是几个本来没关系的地方各自写了同样的补丁。
2. **类型需要逃生舱** — `any`、强制转换、忽略类型检查的注解，或断言成另一个类型才编得过。
3. **函数需要当初签名里没有的参数或额外状态** — 实现时发现「还得再传一个进来」。

按现有的「越权发现」处理：**单独提，不占名额**，但要写清是三条里的哪一条、在哪几个位置。
不要写成「建议重构 X 模块」——那是意见；「同一个绕法在 a:31 和 b:88 各写了一遍，两处没有调用关系」才是事实。

**变更观测表里出现「签名不变但实现改了」「拆分文件、导出不变」「换实现、换库、换数据结构」时，这次改动是重构**，第四条随之生效：

4. **行为是否真的没变** — 重构的验收标准是对外行为不变，所以要主动找**没被声明但实际改掉**的东西：出参字段顺序或空值语义、异常类型、副作用次数（原来调一次现在调两次）、并发或时序假设、默认值、边界取值。这类问题在 diff 上看起来完全合理，只有对照旧实现逐条问「这个输入以前返回什么」才能发现。有测试就跑旧测试；旧测试也一起改了的话，先弄清为什么必须改——**改了旧测试的重构，默认按行为已变对待**。
