# 模块深度审查方法

**加载条件**：SKILL.md §一 判定为「模块深度审查」。

变更审查问「这次改动引入了什么缺陷」，模块审查问的是另一件事：

> **正常路径看起来完全正确，但在重复、并发、异常、越权、重试情况下会失败的地方在哪。**

这类缺陷的共同特征是**单次正常操作永远看不出来**——它们不会被测试覆盖，不会在 code review 里被发现，会一直活到线上出事故那天。找它们需要不同的入口和不同的产出物。

---

## 一、先钉死运行形态

**这是第一步，先于读任何业务代码。**

模块审查里最便宜、重排最多结论的一步。同一段 `SELECT → 判断 → UPDATE`，在单进程串行执行下无害，在多 worker 下就是丢失更新。不钉死运行形态，所有并发结论都不可证伪——写出来也只是「可能有问题」，等于没写。

至少确认这几项，查不到就在报告里写明「未确认」，并把相关结论降为推断：

| 要确认的 | 怎么查 | 为什么影响定级 |
|---|---|---|
| 进程与线程模型 | 启动脚本、`Procfile`、Dockerfile `CMD`、gunicorn / uwsgi / pm2 配置 | 单进程多线程下进程内锁有效；多 worker 下立即失效 |
| 有没有跨进程锁 | 搜 `GET_LOCK` / Redis 锁 / advisory lock / 分布式锁库 | 决定同一业务对象能否真正串行 |
| 数据库隔离级别 | 连接串参数、`SELECT @@tx_isolation`、框架默认值 | 决定事务内读到的是快照还是最新已提交 |
| 定时任务与消费者是不是独立进程 | 调度配置、worker 启动命令 | 独立进程意味着 HTTP 侧的进程内锁保护不到它们 |
| 客户端重试策略 | 前端请求封装、网关配置、MQ 投递语义 | 决定「同一请求到达几次」是假设还是事实 |

**报告第二行必须写运行形态**，因为它是下面所有并发条目定级的前提。

## 二、建写入口清单

**不要逐文件走查。** 模块动辄上万行，逐文件读必然把预算耗在无副作用的代码上——读完了也答不出「这条链路重试会怎样」。

正确入口是**枚举所有产生副作用的入口，逐条追到 SQL**：

| 入口 | 链路 | 落到哪张表 / 写什么 | 并发保护 | 幂等保护 | 前置状态校验 |
|---|---|---|---|---|---|
| `POST /order/confirm` | route → service → repo | `UPDATE orders SET status='paid'` | `WHERE status='pending'`（条件 UPDATE） | 无 | 有 |
| `POST /order/refund` | route → service → repo | `INSERT refunds` + `UPDATE orders` | 事务 | `UNIQUE(order_id)` | 无 ← 候选 |
| MQ `order.paid` | consumer → service | `UPDATE orders` | 无 | 消费者去重表 | 无 ← 候选 |

**清单本身就会暴露问题**，还没开始深挖就能看出来：

- 同一张表 / 同一个字段有几个写入者？多于一个就要问它们是否互相知道对方存在。
- 哪些写入口那一列是空的？空列就是候选问题。
- 哪些保护只是**形状正确**？典型：接口强制要求传 `expected_revision` 并校验它是正整数，但这个值往下传的过程中被丢弃了，从没参与任何比较——校验了形状，没校验语义。
- 同一个业务动作有没有两个入口（比如顾问端一个、老板端一个）？两个入口的校验往往不一致，漏的那个就是漏洞。

**入口要包括非 HTTP 的**：定时任务、MQ 消费者、回调 / webhook、内部工具直调。它们经常绕过 HTTP 层的全部校验。

## 三、拿契约对账

模块通常有接口定义 / 规格文档 / 迁移脚本。**建完清单再读它们**——先建立代码侧的独立理解，再对账。

逐条问：**契约要求的这条约束，代码里落在哪一行？**

「契约写了、代码没做」是模块审查里产出密度最高的一类发现，因为它天然自带证据（契约原文 + 代码位置）和影响（约定被破坏）。常见形态：

- 契约要求某参数必填，路由校验了存在性，但下游从没用它做比较
- 契约定义了状态词表，代码里存在词表外的取值
- 定义好的校验函数 / 装饰器，全仓 grep 只有定义处一处命中——**写了忘了挂**
- 迁移脚本第一部分建表带了某个约束，第二部分补列时漏了——新环境有、存量环境没有

最后一条特别值得查：**建表脚本和增量脚本的约束是否一致**。它决定「DB 兜底」这句话在存量环境到底成不成立。

## 四、四条扫描主线

拿着写入口清单走，不要按文件顺序。

### 4.1 幂等身份跨层盘点

一条链路上通常同时存在三种幂等身份。**混用是模块级缺陷的高发区，而且只有跨层看才看得见**——只看后端找不到，只看前端也找不到。

| 层 | 身份应该是什么 | 语义 |
|---|---|---|
| 传输层 | HTTP `Idempotency-Key`、MQ message id | 这是不是同一**次投递** |
| 事件层 | 领域事件 ID、inbox 主键 | 这是不是同一个**事件** |
| 业务层 | 由不可变业务事实推导，如 `sha256(order_id:refund_reason)` | 这是不是同一**件事** |

逐条问：

1. 每一层的身份**实际**是什么？（不是设计文档写的，是代码里算出来的）
2. 下游用的是哪一层的身份？**用传输层的键去做业务层的去重，是最经典的错法**——用户重试换一个新 key，业务就重复执行一次。
3. 代码里有没有「确定性兜底键」，它在什么条件下才生效？如果写成 `args.get("key") or sha256(...)`，而主路径永远传值，那个兜底就是死代码。
4. 前端生成键的那个函数，**真的按业务身份派生了吗**？调用点传了 seed 不代表函数用了它。

### 4.2 状态机与业务不变量

见 `risk-backend.md`〈状态机与业务不变量〉。模块审查里这条主线通常贡献最多发现，因为状态漏洞既过不了 lint 也过不了测试。

### 4.3 权限的两个维度

模块级越权几乎总是**只做了一个维度**：

- **资源归属** — 这个人和这条数据有没有关系？（查询条件带没带 user / tenant / org）
- **角色与面** — 这个人该不该走这个入口？（顾问端接口能不能被老板调，反之亦然）

只做归属维度时，同一家公司里的不同角色可以互相冒充；只做角色维度时，同角色的不同租户可以互相读写。

**查法**：找到鉴权装饰器 / 中间件的定义，然后 grep 它的引用。**定义了却零引用**是这一类里最常见也最严重的形态——代码看起来有守卫，实际一个入口都没挂上。

顺带查：批量接口是不是逐条校验权限；`actor` 这类字段是路由硬编码的字面量，还是从认证身份推导的。

### 4.4 失败与恢复

对每个写入口问四个问题：

1. **外部副作用已提交、本地状态没提交时会怎样？** 典型：第三方支付已扣款 / 消息已推送给用户 / 文件已上传，随后写库失败抛异常 → 上层按失败重试 → 外部副作用发生第二次。
2. **重试安全吗？** 「第一次请求成功与否未知」时再发一次，业务效果是不是仍然只有一次。
3. **异常会留下半完成状态吗？** 事务边界是否覆盖了所有相关写入；事务外的「事后同步」是不是吞了异常。
4. **失败事实落得下去吗？** 失败处理路径自己带的更新条件，会不会和已经变化的状态互斥，导致失败状态也写不进去——**结果是记录永久卡在中间态，且用户看不到任何错误**。

第 4 条容易被忽略但危害大：正常路径和失败路径都写不进去的记录，不会报警、不会重试、不会超时，只会一直卡着。

## 五、输出形状

模块审查的产出不是「几条问题」，是**一份可逐条修的清单 + 一份归纳**。

### 单条格式

在 SKILL.md 的单条格式上，额外带两项：

```text
[事实] 必须修复 · services/order/refund.py:88
退款幂等键取自 HTTP Idempotency-Key，客户端每次重试都换新值

触发条件：用户在退款页连点两次，或首次请求超时后重试
影响：同一订单产生两条退款记录，实际退款两次
证据：refund.py:88 用 args["idempotency_key"] 作去重键；
     前端 api/refund.js:12 的 idempotencyKey() 每次调用返回新 UUID
边界：MQ 触发的退款不受影响，它用的是 order_id 派生键
建议：改用 sha256(f"{order_id}:{refund_type}") 作业务层幂等键
数据库兜底：需要。refunds 表当前只有主键，建议加 UNIQUE(order_id, refund_type)
```

**「数据库兜底」是模块审查特有的一栏**，回答一个问题：这条业务规则现在只活在代码里，还是有 UNIQUE / NOT NULL / 条件 UPDATE / 行锁 / 乐观锁最终兜住。只活在代码里的规则，换一个调用方就会被绕过。

### 系统性风险（3–5 条）

必须是从**多条发现里归纳出的共性**，不是把发现换个说法重列一遍。

判断标准：如果一条「系统性风险」只对应一条发现，它就不是系统性风险，删掉。真正的系统性风险长这样——「幂等的身份选错了层次，在三处以不同形式出现」「乐观锁被『服务端回读期望值』在六处系统性架空」。

### 明确没发现问题的部分（必出）

列出**认真查过、判定为干净**的部分，写清查了什么、怎么查的、为什么判定干净。

这一段不是客套，有两个实际作用：

1. **它是其余发现的可信度背书。** 读者看到你认真查了核心事务并判定它扎实，才会相信你说别处有问题不是在凑数。
2. **它是下一轮审查的输入。** 省掉重复排查成本。

**这一段不适用「空组不出现」规则**——如果它是空的，说明这轮审查根本没有覆盖面，报告本身就不成立。
