# 证据方法层

本文件是 review skill 的方法层：**怎么算「看到了」**。SKILL.md 规定流程，这里规定每一条发现要拿什么才算数。

评审最容易失败的方式不是漏掉问题，是产出一堆**看起来像发现的话**。写出这种话的成本接近 0，验证它的成本大于 0——所以默认必然滑向前者，只能靠下面的规则挡住。

---

## 一、证据分级

每条问题必须归入三类之一，标签写在最前面。

### 事实

亲眼读到，或亲手跑到。

必须附**具体证据**，二选一：

- 代码位置：`src/auth.ts:42`（精确到行，不写「auth 模块里」）
- 命令输出：跑了什么、输出的哪一句

```text
[事实] 必须修复 · app/services/user.py:117
删除用户时没有清理关联的 session 记录
证据：读到 delete_user() 只执行了 users 表的 delete；
     grep 确认 sessions 表仅在 login 路径写入，无其它清理点
```

### 推断

从事实推出来的。

必须附**一句话推导链**，说清从哪几条事实、怎么推到结论的。

**推导链用人话写，不要用编号互相引用。** 写「key 只用了 userId，而这个方法在 Promise.all 里按 tenant 批量调用」，不写「由事实 2 + 事实 5 推出」——后者读结论时还要回查，等于没写。

```text
[推断] 建议修复 · internal/cache/key.go:88
并发批量调用时 cache key 会碰撞
推导：key 只用了 userID，而这个方法在按租户并发的 worker 池里调用，
     同一用户跨租户的请求会共用同一条缓存
```

推导链写不出来的，它就不是推断，是类比。

### 类比

靠「像什么」得来的。

**永远不能出现在结论里。** 只能进「待验证」段，并标注验证成本。

典型措辞——出现这些词，先怀疑自己：

- 「这看起来像 N+1」
- 「这种写法通常会有内存泄漏」
- 「和上次那个缓存问题很像」
- 「一般来说这里应该加个锁」
- 「经验上这块容易出问题」

```text
待验证
- 这段循环里的 await 看着像 N+1 —— 验证方式：开 SQL 日志跑一次列表接口，
  看查询条数是否随列表长度线性增长。成本：2 分钟
```

要么花那 2 分钟升格成事实，要么老实放在待验证里。**不许偷偷带上严重度混进结论。**

### 严重度只授予事实和推断

| 等级 | 定义 | 处理 |
|---|---|---|
| **必须修复** | 运行期错误、数据错乱或丢失、安全漏洞、线上不可用 | 修复后才能合并 |
| **建议修复** | 有明确影响的性能、维护或项目约定问题 | 建议本次处理，可讨论 |
| **可选改进** | 命名、格式、注释等不影响正确性的内容 | 不阻塞合并 |

类比不带等级。带了就是把猜测伪装成结论。

## 二、验证候选问题

每条候选问题报出前逐条过。**成本最低、杀伤力最大的一步**——比跑测试还便宜，能干掉绝大多数编出来的发现。

### 问一：影响面对得上吗？

如果这条机制成立，相邻调用点、同模式的其它代码也该受影响。

- grep 过引用者了吗？
- 同一份代码里还有几处一样的写法？它们也有问题吗？
- 如果只有这一处「有问题」而其它同款写法都没事，你可能看错了机制。

### 问二：为什么既有代码能够正常运行？

这段代码（或同模式的既有代码）已经在跑，且没人报障——为什么？

- 有没有上游校验兜住了？
- 有没有实际上走不到的分支？
- 是不是这个输入组合现实中不会出现？

**解释不了这个矛盾，就降低严重程度或删掉。** 这一问用于排除凭空出现的严重问题。

**注意：一条测试、一句注释或一段文档说「这样是有意为之」，不构成对这一问的回答。** 那是当时的意图，不是当前的事实。要用它，先核对它描述的场景和手上这个是不是同一件事；对不上就按事实走，并在报告里写明该理由在本例不成立。

新增代码没有「已经在跑」的历史，这一问改成：为什么现有测试没有覆盖到？覆盖了却过了，说明你的判断可能错了。

### 问三：边界说得出来吗？

什么输入、什么条件下**不**发生？

说不出边界，说明只是模糊地觉得不对，还没真正理解这条机制。回去看代码，或改成待验证。

## 三、发送前检查

发出去之前，删掉：

1. **任何只是在复述代码做了什么的条目**——没有失败后果就不是发现。
2. **任何没有位置的条目**——定位不到就没法修。
3. **任何带着严重度的类比**——改为待验证，或继续取得证据。
4. **空的分组标题**——不写「无」，整段不出现。
5. **任何需要回查的编号标志位**（`C01`、`B03`、「见问题 3」）——每条必须自解释：位置 + 现象 + 后果。
6. **超过 5 条之后的同级条目**——合并同类或降低严重程度。五条排好序，胜过十条没排序。
7. **后果只写到代码层的条目**——「死代码」「注释与实现不一致」「契约里没写」是线索不是后果。往下问「谁会卡住 / 能不能自己出来 / 有没有人会知道」，答得出才留，答不出就删。

然后验证三件事：

- 每条问题，作者读完知不知道**改哪儿**？
- 判定（可合并 / 需修复 / 需重做）和列出的问题**对得上**吗？没有必须修复的问题却写「需重做」，或者存在必须修复的问题却写「可合并」，都是自相矛盾。
- 报告里有没有出现**一次都没验证过的运行期断言**？有就改标签。

三件都过，发送。

---

## 四、为什么是这套规则

- **分级而不是「必须给出可复现场景」**：要求每条都写出完整复现步骤会误杀真实但轻量的问题（比如一处确实缺失的空值判断）。分级保留了这类发现，同时把猜测挡在外面。
- **三问而不是更多检查项**：检查项越多，模型越倾向于逐项填充。三问是**减法**——它的作用是删掉候选，不是生产候选。
- **上限 5 条**：评审的价值在排序。不设上限时，真问题会被淹没在凑数条目里，作者读到第三条就开始跳读。

## 反模式速查

出现下列任何一条，停下纠正：

| 反模式 | 症状 | 纠正 |
|---|---|---|
| 复述式发现 | 「这里加了一个循环调接口」被当成问题 | 说不出失败后果就不是发现，删 |
| 审美挑刺 | 把命名或格式偏好写成重要问题 | 降为可选改进，或合并成一条具体风格问题 |
| 后果只写到代码层 | 结论停在「死代码」「注释与实现不一致」「契约没写」 | 这些是线索不是后果。往下问「谁卡住 / 能否自救 / 有人知道吗」，答得出才留，答不出就删 |
| 替产物辩护 | 用既有测试的 docstring、注释或文档里的理由，论证现状是对的 | 那只是当时的意图。先核对它描述的场景与本例是否同一件事；对不上就按事实走，并写明该理由在本例不成立 |
| 为整洁而建议 | 建议写成「统一语义 / 删掉死代码 / 补上文档」 | 先说这条业务路径应该怎么走通，再说代码怎么改；只谈整洁的降为可选改进 |
| 想象型严重问题 | 没跑没查就断言运行期出错 | 标成推断并写推导链，或去跑一次 |
| 填格子 | 为了让分组不空而编内容 | 空组不出现（模块审查的「没发现问题」段除外） |
| 建议未验证 | 给的修法自己没确认能编译 / API 存在 | 标注「未验证」，或查一次文档 |
| 规格先入为主 | 变更审查里先读 PRD 再看 diff | 回到只读 diff 建观测表那一步，重建独立理解 |
| 越权发现（**仅变更审查**） | 结论是「整个模块该重构」 | 超出本次 diff 可干预范围，单独提，不占名额。属〈结构信号〉三条之一的，写清是哪条 + 位置。**模块深度审查里这不是反模式，是正常产出** |
| 逐文件走查（**仅模块审查**） | 从模块第一个文件读到最后一个 | 回到写入口清单，只跟着有副作用的链路走 |
| 并发形状定罪 | 见到 `SELECT → 判断 → INSERT` 直接判定有漏洞 | 先查唯一约束 / 行锁 / 乐观锁 / 条件 UPDATE / 调用方串行，全都没有才升级为确定问题 |
| 全量平铺 | 300 行 diff 逐行点评 | 按代价排序，变更审查每档上限 5 |
| 编号迷宫 | 用 `C01` / `B03` 之类标志位互相引用 | 每条自解释：位置 + 现象 + 后果，读结论不用回查 |
