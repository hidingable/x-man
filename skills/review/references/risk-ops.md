# 脚本与交付链高危项

**加载条件**：diff 里出现 `.sh` / `.bash` / Makefile / Dockerfile / CI 配置（GitHub Actions、GitLab CI、Jenkinsfile）/ 部署脚本 / 子进程调用 / 环境变量与配置文件。

这类代码的共同特点是**平时不跑，出事时才跑**——测试覆盖天然薄，评审是唯一防线。

---

## 一、Shell 脚本

### 变量未加引号

最高频、后果最重的一类。

```bash
# 危险：路径带空格就散架，为空时参数直接消失
rm -rf $BUILD_DIR/*
cp $SRC $DST

# 安全
rm -rf "${BUILD_DIR:?BUILD_DIR is required}"/*
cp "$SRC" "$DST"
```

**怎么查**：搜 diff 里所有裸 `$VAR`。用在路径、文件名、`rm`/`cp`/`mv` 参数上的，一律是问题。`${VAR:?}` 这种在变量为空时直接失败的写法，比事后判断更可靠。

有 `shellcheck` 就直接跑——这一整类问题它能全查出来，比人肉读快且准。跑了才算事实。

### 失败不中断

```bash
#!/usr/bin/env bash
set -euo pipefail   # 缺这行，前一步失败后面照常跑
```

- 缺 `set -e`：构建失败仍继续部署。
- 缺 `set -o pipefail`：管道中间失败被最后一个命令的成功掩盖。
- 缺 `set -u`：变量名打错时当空串用，配合上一条就是 `rm -rf /`。

注意反向情况：脚本里如果有**允许失败**的命令（探测类），要显式 `|| true`，否则 `set -e` 会误杀。

### cd 与相对路径

`cd` 失败后后续命令在错误的目录执行。用 `cd xxx || exit 1`，或全程用绝对路径。脚本自身位置用 `$(cd "$(dirname "$0")" && pwd)` 取。

### 危险操作

`rm -rf`、`chmod -R`、`find -delete`、重定向覆盖 `>`——作用目标是变量拼出来的吗？变量为空时会作用到哪里？

## 二、密钥与配置

- **进代码库** — diff 里有没有 token、密码、私钥、连接串的字面量。包括测试文件和示例配置。
- **进日志** — `set -x` 会把带密钥的命令整行打出来；打印整个环境变量或整个请求体同理。
- **进镜像层** — Dockerfile 里 `COPY` 了密钥再 `RUN rm`，密钥仍留在中间层里。
- **配置优先级** — 新增配置项的默认值是什么？环境变量、配置文件、命令行参数谁覆盖谁？缺失时是报错还是静默用默认值——静默用默认值上线过很多事故。

## 三、容器与镜像

- **基础镜像** — 有没有钉版本，还是用 `latest`。
- **构建缓存** — `COPY . .` 放在 `install` 之前，会让每次改代码都重装依赖。
- **运行用户** — 是否以 root 运行。
- **健康检查与信号** — 容器能否正确响应 `SIGTERM` 优雅退出，还是被强杀。

## 四、CI 与部署

- **重跑幂等** — 这个任务重跑一次会怎样？重复发布、重复迁移、重复推送 tag？
- **并发触发** — 两个 PR 同时触发部署，会不会互相覆盖。
- **失败半途** — 部署到一半失败，系统停在什么状态？有回滚路径吗？
- **权限范围** — CI 用的 token 权限是不是过大（能写主分支、能删仓库）。
- **触发条件** — 新增的 workflow 触发条件会不会意外命中（比如 `on: push` 没限分支，导致每个分支都部署生产）。

## 五、定时任务

- **重叠执行** — 上一次还没跑完，下一次就到点了，会并发跑吗？
- **时区** — cron 表达式按哪个时区解释，服务器时区和预期一致吗。
- **失败可见性** — 任务失败了有人知道吗，还是静默跳过等到出事才发现。
