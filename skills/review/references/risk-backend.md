# 服务端与数据层高危项

**加载条件**：审查范围内出现 SQL / ORM 调用 / 事务 / 锁 / 并发原语（goroutine、线程池、`Promise.all`、`asyncio`）/ 消息队列 / 定时任务 / 接口 handler / 数据库迁移脚本 / 业务状态字段。变更审查看 diff 是否命中，模块深度审查看写入口清单是否命中。

语言无关。下面每条都给了**怎么查**——查不出证据的，按 `evidence.md` 作为待验证假设，不进结论。

---

## 一、事务边界

最高频的服务端缺陷类别，且几乎全部可以静态查出来。

- **写操作是否都在同一个事务里？** 一个业务动作分成两次提交，中间失败就留下半截数据。查：这段逻辑里有几次 commit？
- **事务里有没有外部调用？** HTTP 请求、消息投递、发邮件放在事务内，会把数据库连接占满，且外部调用不可回滚。查：事务块内有没有网络 IO。
- **异常有没有真的触发回滚？** 被 catch 住又没重抛的异常，事务会照常提交。查：catch 块里有没有吞掉异常。
- **框架的事务注解是否真的生效？** 同类内部调用绕过代理（Spring `@Transactional` 是经典），装饰器包错层，手动开启的事务没传下去。查：调用链是从外部进来的还是同类内部调用。

## 二、并发与竞态

- **读改写** — `SELECT → 判断 → INSERT/UPDATE`（`if not exists then insert`、余额先读后减）是**高风险候选模式，但不能仅凭代码形态定罪**。继续查五件事：有没有唯一约束、有没有行锁（`FOR UPDATE`）、有没有乐观锁（版本号 CAS）、写入是不是条件 UPDATE（`WHERE status = 'pending'`）、上游是不是已经串行化（队列、分布式锁、单消费者）。
  五项全无，才能升级为确定问题。**有其中一项时，问题往往不是「会写坏数据」而是「会退化成一个报错」**——比如唯一键挡住了重复插入，但代码把 duplicate key 当未知异常吞成 500，那这是可用性问题不是数据问题，定级完全不同。还要查冲突后的处理：affected rows 检查了吗？duplicate key 走的是哪条分支？
- **共享可变状态** — 单例上的字段、模块级变量、连接对象被多请求共用。查：这个状态在请求之间是否复用。
- **锁的范围与顺序** — 锁太大拖垮吞吐，锁太小护不住；两处以不同顺序拿两把锁会死锁。
- **异步任务的错误** — 起了协程/线程/`Promise` 但没人等结果，异常静默消失。查：有没有 `await` / `join` / 错误回调。

判断竞态时必须按 `evidence.md` 验证候选问题，尤其要回答：这段代码已经在运行，为什么还没有出事？答不上来就改为待验证——很多看似存在的竞态实际被上游串行化了。

## 三、状态机与业务不变量

**触发条件**：代码里出现 `status` / `state` / `stage` / `phase` / `is_xxx` / `xxx_at`（完成时间、取消时间这类语义时间戳），或明显的业务状态字段。

这一类是 lint、类型检查和单元测试**同时**查不出来的——代码不会崩，只会让数据进入业务上不可能的状态。查法是四步，按顺序做，每步都产出可验证的东西：

**① 列出状态列和取值来源。** 每个状态列的合法取值定义在哪：DB 词表（ENUM / CHECK）、代码常量、还是只在契约文档里？**三方不一致本身就是发现**——代码写得进去、DB 存得下来、契约不认的取值，前端就会渲染不出来。

**② 找出每个状态列的唯一写入者。** grep 所有 `SET <状态列> =`。多于一个写入者时，问它们是否互相知道对方存在。派生状态（由其它字段算出来的）尤其要问：算它的地方有几处，算法一致吗。

**③ 对每个写入口问：它检查前置状态了吗？** 常见的错法是只做了乐观锁：`WHERE revision = :rev` 保证了「没人在我之前改过」，但没保证「当前状态允许这个动作」。两者是不同的约束，缺后者就能从任意状态跳到任意状态。

**④ 标出终态，然后 grep 有没有写路径能改终态数据。** 已完成 / 已取消 / 已归档 / 已删除的记录，还能不能被推进、被重复执行、被重新打开。**终态可写是这一类里最高频也最严重的形态。**

配合逐条检查：

- 状态能不能跳跃（`pending` 直接到 `completed`，跳过 `processing`）
- 同一动作能不能重复执行（`update ... set answered = 1` 有没有 `AND answered = 0` 守卫）
- 前端传入的状态有没有被后端直接信任
- 状态修改与关联数据修改是否在同一事务（状态改了、关联记录没写，或反过来）
- 异常中断后会不会留下中间态，且这个中间态**没有任何东西会再推进它**
- 两个并发请求会不会同时基于旧状态推进

### 业务不变量：写成应该返回空集的 SQL

不变量是「这个组合在业务上不可能存在」。**写成 bullet 只能读，写成 SQL 可以验证、可以留档、可以进 CI**：

```sql
-- 已支付订单必须有金额
SELECT id FROM orders WHERE status = 'paid' AND amount IS NULL;
-- 完成时间与状态必须一致
SELECT id FROM tasks WHERE completed_at IS NOT NULL AND status <> 'completed';
-- 同一业务单只能有一条 active 处理记录
SELECT order_id FROM processes WHERE status = 'active' GROUP BY order_id HAVING COUNT(*) > 1;
```

每条不变量都要判定它**靠什么保证**，这决定了它有多可靠：

| 保证方式 | 可靠性 |
|---|---|
| 只靠前端不展示入口 | 不算保证，绕过前端即失效 |
| 只靠一处 Python / Go 的 `if` | 换一个调用方就绕过；新写的入口不会知道有这条规则 |
| 条件 UPDATE / 行锁 / 乐观锁 | 可靠，但只保护走这条代码的写入 |
| UNIQUE / NOT NULL / CHECK / 外键 | 最终兜底，任何写入路径都绕不过 |

**报告里要写清每条规则现在落在哪一层**，以及建议补哪一层。「这条规则目前只活在 `service.py:88` 的一个 if 里」比「建议加校验」有用得多。

## 四、查询与数据访问

- **N+1** — 循环体里发查询。**查法**：开 SQL 日志跑一次，看查询条数是否随集合长度线性增长。没跑过就是类比，不是事实。
- **无界查询** — 没有 `LIMIT`、没有分页、没有时间范围。数据量小的时候不出事，这正是它能活到线上的原因。
- **索引** — 新查询的过滤/排序字段有没有索引？迁移脚本加了字段但没加索引？
- **注入** — 拼接的 SQL / NoSQL 查询 / 命令行参数，参数来自哪里。查：有没有用参数化查询。
- **连接与资源泄漏** — 连接、文件句柄、游标是否在异常路径上也被释放。查：有没有用 `defer` / `with` / `try-finally`，还是只在正常路径关闭。

## 五、幂等、重复执行与结果未知

对每个产生副作用的操作，主动模拟四个场景——**第三个是最危险也最少被考虑的**：

1. 用户连续点击两次
2. 两个完全相同的请求并发到达
3. **请求超时，但服务端实际已经执行成功**（响应在回程丢了，客户端认为失败）
4. 客户端 / 网关 / MQ 自动重试

场景 3 的要害是**客户端和服务端对「这次成功了吗」的认知不一致**。要回答的核心问题是：

> 第一次请求是否成功尚不可知时，安全重试是否仍然只产生一次业务效果？

逐层检查，并**指出实际兜住的是哪一层**：

```
前端防重（按钮 loading / 请求去重）
    ↓  只是 UX 防护，不算幂等保证
API 幂等键（Idempotency-Key / 事件 ID）
    ↓  键是不是稳定派生的？换一次重试就换一个键，等于没有
Service 状态判断（已处理则直接返回）
    ↓  判断和写入之间有没有竞态
DB UNIQUE / 条件 UPDATE / 锁
       最终兜底，任何路径都绕不过
```

**按钮 disabled 和 loading 态只能算 UX 防护，永远不能作为幂等保证写进结论。**

还要查：

- **幂等键怎么来的** — 由不可变业务事实推导（可靠），还是由客户端每次生成（不可靠）。前端那个生成函数**真的用了传进去的 seed 吗**。
- **重试放大** — 失败重试有没有退避、有没有次数上限。
- **部分成功** — 批量操作中途失败，已成功的部分怎么处理；返回体会不会把部分成功报成整体成功。
- **重复的代价是什么** — 重复读无害，重复扣款、重复发货、重复建单是事故。按代价定级，不要一律按高危报。

## 六、鉴权与越权

权限有**两个独立维度**，只做一个是模块级越权最常见的成因：

- **资源归属** — 这个人和这条数据有没有关系。查：查询条件里有没有带当前用户 / 租户 / 组织。
- **角色与入口** — 这个人该不该走这个入口。查：管理端接口能不能被普通用户调；A 端接口能不能被 B 端角色调。

只做归属维度时，同一组织内的不同角色可以互相冒充（普通成员调管理接口、乙方调甲方接口）；只做角色维度时，同角色的不同租户可以互相读写。

其余：

- **每个新增接口都要问：谁能调？** 有没有挂上鉴权中间件，还是漏在白名单里。**查法是找到守卫的定义，然后 grep 它的引用**——「定义了却零引用」是这一类里最隐蔽的形态：代码里看得见守卫，实际一个入口都没挂。
- **租户隔离** — 多租户系统里，查询、缓存 key、文件路径是否都带了租户维度。缓存 key 漏租户是典型的串数据路径。
- **身份来源** — 记录里的 `operator` / `actor` / `created_by` 是从认证身份推导的，还是从请求体里读的、或路由里硬编码的字面量。后两者等于让调用方自己填署名。
- **批量接口** — 是逐条校验权限，还是只校验了第一条 / 只校验了外层容器。
- **敏感字段** — 返回结构里有没有把密码哈希、内部 id、他人手机号带出去。
- **异常信息** — 原始异常字符串（尤其 DB 驱动的）直接回给客户端会泄露表名、列名和 SQL。查：错误处理的兜底分支是透传 `str(exc)` 还是固定文案。

## 七、外部依赖与失败恢复

- **超时** — 每个外部调用都设了超时吗？没设超时的 HTTP 客户端会一直挂着，最终拖垮整个服务。
- **失败处理** — 下游挂了，本接口的行为是什么：报错、降级、还是静默返回空？
- **数据信任** — 外部返回的数据有没有做结构校验就直接用。
- **副作用已提交但状态没提交** — 第三方已扣款 / 消息已推送给用户 / 文件已上传，随后写库失败抛异常 → 上层按失败重试 → **外部副作用发生第二次**。查：外部调用成功之后的代码，抛异常会导致整体重试吗。
- **失败事实落得下去吗** — 失败处理路径自己带的更新条件，会不会和已经变化的状态互斥，导致失败状态也写不进去。**结果是记录永久卡在中间态：不报警、不重试、不超时，只会一直卡着，用户看不到任何错误。**

## 八、Schema 变更

- **兼容顺序** — 新代码配旧库、旧代码配新库，两种组合在滚动发布期间都会真实出现。删列、改列类型、加非空约束都需要分步。
- **回滚路径** — 这个迁移能回滚吗？回滚后旧代码还能跑吗？
- **大表操作** — 加索引、改列在大表上会锁表多久？
- **默认值与历史数据** — 新增非空字段时，存量行怎么填。
