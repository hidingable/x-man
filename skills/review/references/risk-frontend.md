# 前端高危项

**加载条件**：审查范围内出现 `.css` / `.less` / `.scss` / styled-components / `className` / 组件文件 / 前端依赖变更 / 任何发请求的组件。变更审查看 diff 是否命中，模块深度审查看链路是否经过前端。

不触发就不要加载——审后端或脚本时打开这个文件，等于把预算花在不存在的风险上。

下面每一条都给了**怎么查**。查不出证据的，按 `evidence.md` 作为待验证假设，不进结论。

---

## 一、样式污染

### 全局选择器

改动引入的类名，会不会命中本组件之外的元素？

```less
// 危险：全局生效，改一处炸别处
.header { ... }
.table { ... }

// 安全：带模块前缀，或走 CSS Module / scoped
.alert-history-header { ... }
```

**怎么查**：拿新增的类名去全局 grep。命中多处且分属不同模块 → 事实级污染。只命中本文件 → 没问题。

### UI 库样式覆盖

```less
// 正确：限定在自己的容器内
.custom-modal { .ant-modal-header { ... } }

// 错误：全局改掉库的样式，升级即碎
.ant-modal-header { ... }
```

**怎么查**：搜 diff 里裸露的 `.ant-*` / `.el-*` / `.mui-*` 等库前缀选择器，看有没有被自有类名包住。

### `!important` 与选择器权重

`!important` 本身不是问题，**为了压过自己写的另一条规则**而加的才是。查它压的是谁：压库样式可接受，压自家样式说明层叠已经乱了。

### 样式隔离方式

组件级样式是否走了 CSS Module / scoped / styled？`:global()` 的每一次使用都要能说清为什么必须逃逸。

## 二、依赖版本与 API 匹配

**先确认版本，再判断 API。凭记忆判断 API 存不存在，是这一类误报的唯一来源。**

怎么确认：读 `package.json` + lockfile 里的实际版本；不确定该版本有没有某个 API 时，去 `node_modules` 里查实际导出，或查对应版本的文档——不要凭印象。

常见版本断层：

| 库 | 断层 |
|---|---|
| React | 16.8 前无 Hooks；18 起并发渲染，`useEffect` 在严格模式下双调用；19 起部分 API 变更 |
| React Router | 3.x `hashHistory` / 5.x `useHistory` / 6.x `useNavigate` |
| 状态管理 | Redux `connect` + `mapStateToProps` / Redux Toolkit / Zustand `create` / Context |
| UI 库 | Form、Table 分页、Modal 静态方法、Message/Notification 在大版本间签名常变 |
| 日期 | Moment 与 Day.js 的 API 相似但不等价，插件体系不同 |

新增依赖：这个依赖是必要的吗？项目里有没有已经在用的同类库？

## 三、渲染与状态

- **Hooks 规则** — 是否在条件分支或循环里调用。这条 lint 通常能查出来，先看 lint 有没有跑。
- **`useEffect` 依赖项** — 缺依赖导致读到陈旧闭包；多依赖导致重复执行。判断时要说清具体哪个变量、会读到什么旧值。
- **列表 key** — 用 index 当 key，且列表会重排或增删时才是问题；纯静态列表不是。
- **重渲染** — 只在能指出具体触发链时才报（哪个 state 变了 → 哪些组件跟着重渲染 → 代价是什么）。说不出链条的「可能有性能问题」是类比。

## 四、请求生命周期与竞态

**触发条件**：组件里发请求（`fetch` / axios / SWR / React Query / 自建 hook）。

这一类的共同特征是**开发时点得慢，永远看不出来**——只有快速切换、弱网、连点才暴露。

### 旧请求覆盖新请求

```
用户选 A  → request(A)
用户改选 B → request(B)
           ← response(B)   页面显示 B ✅
           ← response(A)   页面被 A 覆盖 ❌
```

筛选条件切换、搜索联想、分页快翻都会触发。**怎么查**：发请求的地方有没有 `AbortController`，或单调递增的 sequence / generation token，在 `set` 之前比对一次。两者都没有、且这个请求的参数会被用户快速改变 → 事实级竞态。只在挂载时发一次的请求不算。

### 逐条检查

- **重复提交** — 提交按钮在请求进行中会不会被再次触发。**`disabled` 只是 UX 防护**，判断幂等要看后端（见 `risk-backend.md`〈幂等、重复执行与结果未知〉）。
- **loading 在异常路径恢复了吗** — `setLoading(false)` 只写在 `try` 里，抛异常后按钮永久卡死。查：有没有 `finally`。
- **卸载后 setState** — 请求返回时组件已经卸载。现代 React 不再警告，但会造成状态写进已废弃的闭包，配合轮询会一直跑下去。查：cleanup 里有没有取消或置 generation。
- **`useEffect` 重复触发副作用** — 依赖数组里有每次渲染都新建的对象 / 函数，导致副作用反复执行。要说清具体是哪个依赖。
- **StrictMode 双执行** — 开发环境下 effect 会跑两次。**它不是 bug，它是探针**：双执行暴露出问题，说明这个副作用本身不幂等，生产环境在别的时机同样会出事。
- **失败后旧数据被当成最新** — 请求失败时既不清空也不标记，页面上的旧数据看起来仍然是当前值。加载态、空态、错误态、陈旧态要能区分——「加载中」被渲染成「无数据」是高频问题。
- **乐观更新失败回滚** — 先改 UI 后发请求，请求失败时有没有回滚，回滚后会不会和其它已到达的更新打架。
- **刷新后状态恢复** — 流程是否依赖只存在于内存里的状态（上一步的返回值、临时 token）。用户刷新页面或从外部链接直接进入该步骤时会怎样。

### 跨层的那一类

有些前端缺陷**只能从后端倒推回来**，靠前端清单查不到。最典型的是幂等键——调用点看起来是按业务身份稳定派生的：

```js
headers: { 'Idempotency-Key': idempotencyKey(`${taskId}-${action}`) }

function idempotencyKey() {          // ← 不接收任何参数
  return crypto.randomUUID()         // ← 实参被静默丢弃，每次都是新键
}
```

JS 对多余实参不报错，lint 和测试全部通过，前后端的幂等约定就此断掉，而两侧的代码单看都没毛病。

查法：从后端的去重逻辑出发，看它依赖的键前端是怎么生成的，而不是从前端代码往下读。模块深度审查里这条主线见 `module-review.md`〈幂等身份跨层盘点〉。

## 五、前端安全

- **XSS** — `dangerouslySetInnerHTML` / `v-html` / 直接拼 DOM，输入来自哪里？有没有过消毒？
- **密钥外泄** — 前端代码里的 API Key、token、内网地址，会随 bundle 发到浏览器。搜审查范围内的字面量。
- **权限只做在前端** — 隐藏按钮不等于禁止操作。对应的后端接口有没有校验？查不到后端就明确标注「前端已隐藏，后端校验未验证」；能查到后端时按 `risk-backend.md`〈鉴权与越权〉的两个维度过一遍。

## 六、错误与降级

- 异步请求失败时页面呈现什么？空白、旧数据、还是错误提示？（逐条见〈请求生命周期与竞态〉）
- 有没有错误边界兜住渲染期异常？
- 后端返回的错误信息**直接渲染给用户**时，里面会不会带着原始异常串（表名、SQL、内部路径）。
