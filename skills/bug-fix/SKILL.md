# Bug 修复

目标是让原始用户路径恢复正确，并证明产生问题的机制已经处理，而不只是让报错消失。用户、缺陷单、日志或模型给出的原因都先当作待验证的假设。调查可以查宽，修复收窄到已证实问题的最小完整边界。授权按 `.ai-configs/conventions.md`〈授权、实现判断与验证〉。

## 先建一个能变红的回路

按大致顺序找：能走到 bug 的失败测试 → 对运行中服务的 curl 或脚本 → 固定输入跑 CLI 并对比输出 → 驱动界面的无头浏览器脚本 → 回放抓到的真实请求或日志 → 只起一小部分系统的临时脚本 → 随机输入循环找失败 → 能 `git bisect run` 的二分脚本 → 新旧版本同输入对比。必须有人操作时，写清可重复的步骤和要采集的信号。

做完的标志：能给出**一条已经实际跑过的命令**（附上运行结果），并且它：

- 走到真实出问题的代码路径，判断的是用户报告的那个症状，而不只是「没报错」；
- 每次结果一样（间歇问题：复现率已经稳定在能调试的水平）；
- 几秒内跑完。

建不起来时，停下来说明试过什么，向用户要能复现的环境、脱敏后的日志或抓包，或者加临时观测的许可。

间歇或并发故障的目标是提高复现率：循环触发、加并发、缩短时间窗口。一次没复现不代表问题消失。

原因不明显时，回路变红后先缩小复现：输入、调用方、配置、数据和步骤一次删一项，每删一项重跑回路，直到再删任何一项都会变绿。剩下的场景缩小了候选原因，也直接用作回归测试。

## 开始前

1. 读项目上下文、工作区状态和用户给的完整报错；记下与本问题无关的现有改动，后面不碰它们。
2. 从当前有效的需求、接口或数据契约和真实业务状态确认预期行为；旧版本和过往实现单独不能证明当前要求。
3. 写清预期行为、实际行为、复现条件、不出问题的边界，以及每条结论的事实来源。
4. 看起来像笔误、绕远路或反直觉的代码，先假设是故意写的：用 `git log -L` 或 `git blame` 查来历。找不到理由再当 bug 处理，并在说明里写「查过历史，没找到这样写的原因」。把故意的写法当 bug 改掉，会让当初那个坑重新出现。

现象单一、根因位置明确、影响在一个模块内时，走最短路径：复现 → 找到第一次出现异常状态的地方 → 修 → 跑回归。跨模块或跨端、间歇复现、有多个候选原因、涉及权威数据或公共契约、线上已有影响时，走下面的完整流程。

## 定位根因

1. 画出完整失败序列：入口 → 输入 → 调用与规则 → 第一次异常状态 → 传播 → 用户看到的结果。按证据跨越客户端、服务端、权限、数据层、异步任务和外部依赖，一直追到第一次异常状态。
2. 有多个合理解释时，列出有证据支持的候选，每条写一个可证伪的预测（「如果是 X，改变 Y 后会看到 Z」），先验证成本低、能排除最多分支的。证据已经指向一个原因时直接验证。
3. 用日志、测试、断点、版本差异或只改一个变量的实验验证。
4. 搜索所有读取方、写入方、调用方和相似实现，确认影响范围，以及其他边界为什么没出问题。

根因须解释触发、机制、证据、现象和正常边界；未确认前继续采证，不用空值保护、吞异常或改夹具遮住症状。

相邻问题同时满足「有证据、和当前根因或回归直接相关、不处理会影响本次结果」才进入本次修复，否则记进「本次不做」。缺少的信息会改变根因或修复边界时，按〈表达与命名〉的提问规则问。

临时日志加唯一前缀（如 `[DEBUG-a4f2]`），验证完按前缀全部清理并确认没有残留；需要长期保留的改成正式日志。

## 修复

- 真有取舍时才比较几种修法，用实际名称（「只屏蔽异常」「修正状态来源」）。选能处理根因且影响最小的。
- 修改前推演写入方、读取方、下游调用、状态恢复、权限、安全、兼容性和失败路径。
- 先写或运行能稳定证明原问题的回归测试；无法自动化时写清可重复的人工验证步骤。
- 修复权威数据、契约或状态机制时，同步必要的调用方、数据迁移、配置和错误反馈。「最小」指不扩大范围，必要链路一处不漏。
- 每一处修改都能说清和根因、需求、验收、回归保护或必要迁移的关系。
- 现有的正常交互、业务门槛和数据含义保持不变；根因或需求没要求的确认步骤、提示、兼容分支和兜底规则不加。
- 同一业务状态在持久化、接口和界面上读同一个权威来源；后续步骤失败时，已经成功的前置步骤保持成功，分别给出结果和恢复动作。
- 错误反馈指出可定位的问题；业务允许人工处理时，给出可执行的修正或重试入口。

### 线上正在出问题时

用户明确说是线上故障，或证据显示影响还在持续时：

1. 先用影响最小的方式恢复用户路径（回滚、开关、临时兜底），说明这是临时措施。
2. 记下技术债，四项写全：临时做法、根因是否已确认、不治本的风险、什么时候治本。
3. 止血后继续定位根因，现象消失不等于结束。

其他问题不走这条路，「先让它跑起来」是这套流程里最常见的伪装。

## 验证

运行真实链路前核对服务、异步 worker 的版本、任务与权限；版本不明时，不把结果归因于本轮代码。

先跑最接近根因的回归，再扩到受影响模块和真实用户路径，覆盖：原始复现路径、不出问题的边界、受影响的调用方和失败路径，以及实际涉及的持久化、状态恢复、权限、并发、异步任务和外部依赖。

自动化检查通过后，再确认原始现象确实消失。代码修复、本地验证、数据修复、提交、部署、真实页面或设备验收是不同层级，逐层报告。

### 环境与外部阻塞

同一阻塞经两次独立检查确认，或排查 10 分钟没有新证据时，停止重复请求、等待和重启，说明阻塞证据及未验证范围；条件变化后再试。继续不依赖阻塞的修复与最小验证，替代任务或环境已有授权时直接使用，原环境仍标为未通过。新增依赖、启动数据库或寻找发布入口，仅在完成目标必需且授权覆盖时进行。

## 输出

1. **修复结果**：用户可见的行为现在怎样。
2. **根本原因**：一句话机制，加证据位置。
3. **修复边界**：改了什么、为什么足够、数据影响、保留了哪些正常行为。
4. **验证结果**：实际执行的命令或操作，以及它证明到哪个层级。
5. **未验证事项**：有才写。

引用日志、抓包或配置前先脱敏：密钥、token、连接串、真实用户标识替换成 `<REDACTED>`，凭据走环境变量。日志只引用携带信号的那几行。

需要留档时用 `assets/templates/fix-report-template.md`。复杂故障需要更多排查手段时，读 `references/bug-fix-guide.md`。故障反常、几轮假设都被推翻时，读 `references/first-principles.md`，从可查证的约束重新拆。
