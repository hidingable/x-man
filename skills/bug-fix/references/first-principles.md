# 第一性原理拆解

故障反常、几轮假设都被推翻，或常见解释都对不上现象时读。
从“确切知道什么”开始，不从“最像什么”开始。只产出拆解结论和证伪方法，不继续实施。

## 拆解

### 还原可观察事实

把“发生了什么”和“为什么发生”分开。每条事实都附来源，例如命令、日志、代码、规格、原话、时间或版本。

同时写清边界：

- 什么情况下发生，什么情况下不发生。
- 最后一次正常是什么时候，中间改变了什么。
- 换环境、账号或输入后是否仍然发生。

事实不足时先自行采集。无法自行获得、且不同答案会改变拆解方向或结论时，停下来说明当前事实和缺口，按〈表达与命名〉的提问规则确认。

### 剥离解释和类比

每条陈述只使用完整语义名称，并归入：

- **已验证事实**：能给出复核方式。
- **由事实支持的判断**：写清推导链。
- **尚未验证的假设**：说明验证成本和一旦为假会推翻什么。

类比只能产生假设，不能进入最终结论。禁止使用 `F1`、`A1`、`O1` 等编号标志位。

### 比较有依据的候选解释

事实支持多个合理解释时，将它们列出并比较；证据已指向一个解释时直接检验，不为凑数补造候选。候选数量由事实决定。

- **每条写出可证伪预测**：如果解释成立，改变某个条件会看到什么，什么结果会推翻它。说不出预测时，先补清解释或移出候选。
- **安排验证顺序**：优先做成本低、能排除更多分支的检查。结果与预测不符时，更新或放弃解释，不只寻找支持证据。

向用户同步会改变判断的候选和依据。仅在缺少无法自行取得的关键事实时提问，其余调查继续推进。

### 拆到可干预的约束

对最反常的事实递归问“凭什么”，把每个必要条件都展开。停止在能被查证、且能施加干预的最浅一层：

- 物理或数学约束。
- 源码、协议、规格或已验证业务规则。

“框架就是这样”“历史原因”“最佳实践”都不是停止条件。

### 从底层重建

从约束和事实正向推出预测，再与全部现象和边界对账：

- 是否解释了所有现象。
- 是否会推出一个本应出现、但实际没有出现的现象。
- 是否能解释问题不发生的边界。

任一项对不上，就回到未验证假设继续拆。

### 设计证伪实验

用只改变一个变量的最小实验尝试推翻结论。实验必须提前写清：

- 如果结论成立，会看到什么。
- 如果结论错误，会看到什么。
- 实际结果如何改变当前判断。

无法出现“我错了”的结果，就不是证伪实验。

## 输出

默认只写：

1. **结论**：一句话说明根本原因、底层诉求或基本约束。
2. **依据链**：约束 → 已验证事实 → 推导 → 与现象对账。
3. **被排除的解释**：只写最容易误导决策的内容。
4. **证伪结果**：实验、实际结果、结论是否仍成立。
5. **尚未闭合**：只在存在时写未验证分支和影响。

拆解结论直接用于后续的定位和修复；需要单独留档时按 `.ai-configs/conventions.md` 的 analysis 路径保存。

### 表达规则

通用规则见 `.ai-configs/conventions.md`〈表达与命名〉，核心一条：事实、假设和结论用实际含义引用，不用 `F1`、`O1` 这类代号——推导链写「因为登录接口每次都走 DB」，不写「由事实 2 推出」。这里另外要求：

- 先写结论，再写推导；不写完整调查流水账。
- 不用表格堆积事实；只保留会改变结论的信息。

## 查故障时的具体做法

### 这一档里的三个层次分别是什么

| 通用概念 | 查问题场景下的具体所指 |
|---|---|
| **观测** | 日志行、报错栈、返回码、耗时数字、监控曲线、复现步骤与复现率 |
| **公理** | 语言/运行时语义、框架规格文本、协议 RFC、操作系统与网络的物理约束 |
| **重建** | 从公理正向推出「在当前代码和输入下，必然会发生什么」，与日志对账 |
| **证伪** | 改一个变量后，预测的日志/耗时/返回值会变成什么 |

### 事实采集清单（观测不足时先执行）

按顺序，**不要跳过前三条直接读代码**：

1. **完整报错栈**（不是截断的最后一行）——第一个自己代码的帧在哪
2. **精确复现步骤 + 复现率**（5 次里几次）——偶发和必现是两种问题
3. **时间/版本边界**——最后一次正常是什么 commit / 什么时间；`git log`、`git bisect` 的可行性
4. **入参实际值**（不是你以为的值）——打印出来
5. **环境差异**——本地 vs 测试 vs 线上，哪个发生、哪个不发生
6. **不发生的边界**——换账号？换数据？换并发度？换时区？

### 这一档最常见的隐性假设

打 `[假设]` 标签，别当事实：

- 「这段代码在跑」——加日志确认它被执行了
- 「跑的是我改的那份」——确认部署版本 / 构建产物 / 缓存的 bundle
- 「报错的地方就是出错的地方」——异常抛出点 ≠ 状态被写坏的点
- 「配置是我看到的那份」——环境变量、覆盖顺序、多份 config 合并
- 「这两个是同一个对象/连接/实例」——单例真的单例吗？连接池换实例了吗？
- 「时间是线性的」——并发、重试、时钟漂移、时区
- 「上一个修复生效了」——它验证过吗，还是只是「改完看着好了」

### 追问模板

```
凭什么认为 X 该发生？        → 找到那条规格 / 那行代码
凭什么认为 X 没发生？        → 找到那条观测，不是「感觉没有」
X 发生需要哪些必要条件？      → 全部列出，逐条打 ✓/✗/★
最早哪一步和预期分叉的？      → 沿数据流向上走，不要在报错点原地打转
如果这是根因，还应该出现什么？ → 那个东西实际出现了吗
```

### 二分法与拆解树的关系

拆解树告诉你**沿哪条链二分**，二分告诉你**在链上哪一点断**。两者配合：

- 数据流二分：入口 → 中间层 → 出口，在每一段边界打印实际值，找第一个不符预期的点
- 版本二分：`git bisect`，前提是有明确的「好/坏」判定脚本
- 配置二分：最小可复现配置 → 逐项加回

**先用拆解树砍掉不可能的分支，再在剩下的最长链上二分。** 直接对全量二分是浪费。

### 停止条件

拆到**「能施加干预的最浅一层」**就停，不要继续往下：

- ✅ "同类内部调用不走 Spring 代理" —— 可干预（self-inject / 拆 bean）
- ✅ "JS Number 是 IEEE754 双精度，2^53 以上丢精度" —— 可干预（用 BigInt / 字符串）
- ❌ 继续拆到 "为什么 IEEE754 这么设计" —— 无法干预，是浪费

### 完成后的现实动作

根因确认且证伪实验支持结论后，直接说明需要修改的机制、修复边界和必须保留的回归证据。后续由用户或外部编排决定。
