# Bug 修复方法补充

仅在故障跨模块、间歇出现或存在多个候选原因时读取。

## 建立失败序列

```text
用户动作 → 实际输入 → 调用链 → 第一次异常状态 → 可见错误
```

每一跳附文件、日志或实验依据。报错位置只表示错误被发现，不一定表示状态在那里被破坏。

## 缩小范围

- 对数据流，在入口、中间边界和出口记录实际值。
- 对版本变化，找到最后正常和首次异常版本。
- 对环境差异，逐项比较配置、数据、权限和依赖。
- 对间歇问题，记录时间、并发、重试和资源状态。

先验证能排除最多分支、成本最低的假设。

候选原因不超过当前证据能支撑的数量。每个候选原因都要写“如果成立会看到什么”和“什么结果会推翻它”，不能只列常见问题清单。

## 判断是否找到根因

根因应同时解释：

- 为什么当前条件会失败。
- 为什么其他边界不失败。
- 如果机制成立，还会出现什么现象。
- 改变一个关键变量后，结果为什么会变化。

解释不了任一项，就继续调查。

## 选择修复

如果存在多个做法，按实际目的命名，例如：

- **只屏蔽异常**：改动小，但根因仍存在。
- **修正权威数据来源**：处理根因，需要同步调用方。

说明收益、代价、兼容性和回归路径。不要用字母方案或“第一刀/第二刀”。

修复前检查：

- 修正的是最早异常状态，还是只处理了后续报错。
- 权威数据、公共契约和权限边界是否仍然正确。
- 所有必要读取方、写入方和调用方是否同步。
- 是否需要迁移历史数据、清理缓存、更新配置或兼容旧版本。
- 失败时用户是否得到明确反馈并能够恢复。

## 验证

先跑最小回归，再扩大到受影响模块。验证记录保留命令、关键结果、真实用户路径和无法执行的部分。命令通过后仍需确认原始用户路径、正常边界、数据恢复和失败反馈。
