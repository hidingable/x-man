# 需求诊断方法补充

仅在需求证据冲突、影响面复杂或根本原因难以确认时读取。

## 从方案退回问题

把“加导出按钮”“引入缓存”“重做架构”改写为：

- 谁在什么场景遇到什么阻碍。
- 当前结果与期望结果差在哪里。
- 这个差距带来什么可观察代价。
- 提出的方案通过什么机制缩小差距。

如果机制链说不通，先不要评估方案。

## 根本原因检查

### 用户需求

追到目标与现有流程之间的断点。用户原话是证据，但用户给出的解法仍需验证。

### 异常修复

追踪实际入口、输入、调用链、状态变化和失败边界。报错位置不一定是状态最早被破坏的位置。

### 技术重构

用重复故障、交付时间、变更风险或维护成本证明问题。审美偏好不是重构理由。

## 影响面

从变化的事实源向外检查：

- 读取者和写入者。
- 权限、校验和错误处理。
- 数据迁移与兼容。
- 用户入口、状态和下一步。
- 自动化测试、监控和归档。

只列实际受影响项，不复制整棵目录树。

## 方案对比

没有真实取舍时不要强行多方案。需要比较时，每个方案写：

- 实际名称和核心做法。
- 如何处理根本原因。
- 有依据的时间范围。
- 风险、适用条件和回退方式。

推荐放第一，并说明什么证据会改变推荐。

## 完成标准

标准要能执行：

```text
角色 + 前置条件 + 动作 + 可观察结果 + 失败反馈
```

“性能更好”“体验更顺畅”“系统更稳定”必须改成指标或明确的人工确认方法。

## 写作

对话先给一句结论和不超过五条依据。留档使用模板，删除空章节。标题使用实际问题、方案和风险名称，不使用字母方案、问题编号、阶段编号或置信度标签。
