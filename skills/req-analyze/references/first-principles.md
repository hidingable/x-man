# 从第一性原理看需求

用户带着解法来、底层诉求说不清，或几种说法互相打架时，按以下步骤拆解：

1. **还原事实**：记录谁在什么场景遇到什么困难、目前怎么处理，给关键事实附来源。
2. **剥离假设**：把已验证事实、由事实支持的判断和待验证假设分开。标出哪个假设一旦推翻就会改变诉求。
3. **从约束重建**：找出用户必须达成的状态和不可协商的约束，推导能解决问题的做法，再核对原方案覆盖了什么。
4. **设计证伪实验**：选成本最低的验证，提前说清会支持或推翻诉求判断的结果。

有人提了个要求，但底层想解决什么不清楚。**注意：这一档拆的是「诉求」，不是「方案」。** 绝大多数需求描述其实是一个已经被提出者内部翻译过一遍的解决方案。

## 四个概念在需求场景中的含义

| 通用概念 | 探讨需求场景下的具体所指 |
|---|---|
| **观测** | 谁、在什么时刻、做了什么动作、卡在哪、原话是什么、发生频次 |
| **公理** | 提出者真正要达成的状态，以及不可协商的约束（合规、成本、能力边界、组织现实） |
| **重建** | 从底层诉求出发，独立推导出解法空间，看原方案是否落在里面 |
| **证伪** | 一个最小验证：如果诉求是我说的那个，做 X 应该能让指标动 |

## 需求归零：把方案还原成诉求

每一条需求描述过一遍这张表：

| 提出者说的（方案） | 归零后（诉求 + 观测） |
|---|---|
| "加个导出 Excel 按钮" | 观测：财务每周一手动截图 12 张表贴进邮件，耗时约 40 分钟。诉求：周期性把数据交到财务手上。 |
| "把列表改成无限滚动" | 观测：运营说「翻页翻到第 7 页就烦了」。诉求：在长列表里快速定位目标行。（可能真答案是搜索，不是滚动。） |
| "要个 AI 助手" | 观测：新人问了 30 次同一个流程问题。诉求：把流程知识送到新人手边。 |

**归零操作：对每个方案词问一遍「这个动作是为了达成什么状态？」，答到不能再答。**

## 追问模板

```
这个需求解决的是谁的什么困难？    → 要具体到人和场景，不接受「用户」
最后一次这个困难发生是什么时候？   → 说不出来 = 可能是想象出来的需求
现在他们怎么绕过去的？            → 有 workaround 说明痛感有限；没有说明是真堵死
不做会怎样？                     → 说不出后果 = 优先级为 0
凭什么认为这个方案能解决那个困难？ → 中间的推导链让他讲一遍，通常这里就断了
这个方案失败的话，困难还在吗？     → 在 = 方案和诉求没对齐
谁提的？是他的困难还是转述的？     → 转述会丢失约束，回源
```

## 这一档最常见的隐性假设

- 「提出者说的困难 = 真实困难」——转述、抽象、面子，都会失真。回源到一手场景。
- 「频次高 = 重要」——高频低痛 vs 低频致命，是两码事。
- 「用户要 X 就是需要 X」——用户擅长描述症状，不擅长设计解法。
- 「这是新需求」——查一下是不是已有功能没被发现 / 没被用起来。
- 「没有约束」——预算、合规、上下游依赖、组织边界，问出来再说。

## 从底层诉求重建解法

**不要**从原方案往回论证。从底层诉求出发**独立推导解法空间**，至少列 3 条路径，然后再看原方案落在哪：

```
诉求：周期性把数据交到财务手上
  ├─ 导出按钮（原方案）—— 仍需人工触发和发送
  ├─ 定时任务自动发邮件 —— 完全去掉人工，但要处理异常和权限
  └─ 给财务开只读看板 —— 去掉「交付」这个动作本身
对账：原方案只解决了「取数」，没解决「送达」——它落在解法空间边缘。
```

如果原方案不在推导出的空间里，或只覆盖了诉求的一部分 → **这就是本次拆解最有价值的产出**，明确写出来。

## 证伪实验

需求档的实验通常是**低成本探针**，不是上线：

- 拿 3 个真实用户的真实数据手工做一遍，看诉求是否被满足
- 一张静态图 / 一段假数据 demo，问 "这样解决你的问题吗"
- 先埋点量一周，看假设的频次是否真的存在

**可证伪性要求**：必须能说出「如果跑出 XX，说明我对诉求的判断是错的」。

## 停止条件

拆到**「提出者不可协商的目标状态」**为止。再往上（"为了公司战略"）不可干预，是浪费。

## 完成后的现实动作

诉求明确后，和用户确认下一步是补充事实、比较方向、形成需求边界还是开始实施规划。
