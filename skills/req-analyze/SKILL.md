# 需求诊断

先确定真实问题和根本原因，再讨论方案。只交出诊断结论；需求文档、实施计划和代码是后续阶段的事。授权按 `.ai-configs/conventions.md`〈授权、实现判断与验证〉；工程约束按 skill 安装目录里的 `create-plan/references/engineering-checks.md`。

需要和用户多轮确认的事，按 `references/grilling.md` 的追问方法进行。

## 只追问模式

用户说「只追问」「先帮我想清楚」「拷问一下这个方案」，或者只是想把一个想法、计划磨清楚时，按 `references/grilling.md` 追问到双方理解一致，不写分析文档。追问中遇到业务名称含义冲突或含糊，调用 Skill 工具（参数为 `domain-terms`），定下来的含义当场记进项目上下文。

## 开始前

1. 按 `.ai-configs/conventions.md` 读取项目上下文和已有 analysis 产物。
2. 读取与需求直接相关的代码、配置、日志、用户原话或数据。
3. 区分用户已确认的决定、可验证事实、由证据支持的分析判断和尚待验证的假设，写清来源和适用条件。用户决定说明要做什么，不自动证明现状或根因；分析建议不能写成用户决定。

诊断中遇到影响目标、业务规则、状态或权限的名称时，调用 Skill 工具（参数为 `domain-terms`）核对含义，在结论中写清含义、依据和适用边界。

## 诊断姿态

这个 skill 的价值在于敢追问。方法能约束怎么查，姿态决定查不查得下去——下面几条不写，模型会默认退回附和。

- **第一个答案要用事实核对。** 「提升用户体验」要追到「哪个页面的哪个操作、谁在什么时候被卡住」；证据充分时直接收敛，不为追问增加轮次。
- **每个回答都要表态。** 说清你现在的判断，以及什么证据会改变这个判断。只复述用户的话不算诊断。
- **认出常见失败模式并直接说破**，不要绕：
  - **方案找问题**——先有了想做的东西，再倒推一个需求
  - **假想用户**——「用户应该会需要」，但说不出具体是谁、什么时候说过
  - **完美主义拖延**——真正的阻碍是不想开始，不是缺这个功能
  - **代理指标**——要的是「让报表好看」，不是报表背后那个决策
- **不迎合。** 用户说「这个需求很简单」而代码事实不支持时，说出差距和依据。用户不接受时，把分歧写进报告，不改成他想听的版本。
- **追问依据是证据缺口。** 只追问会改变判断的缺口；诊断深度由证据决定，和对话尖锐与否无关，对事不对人。

追问的边界：用户明确表示不想继续讨论、或要求按现状推进时，停止追问，把未闭合的风险写清后继续。

## 诊断

需求性质会改变诊断重点时，先向用户确认是新功能、功能增强、异常修复还是技术重构；上下文已经明确时不重复问。

### 说清真实问题

确认以下信息；已有证据覆盖的内容不再追问：

- 谁在什么场景受阻，实际代价是什么。
- 当前如何处理，为什么现有方式不够。
- 期望改变的是结果，还是用户已经预设的实现手段。
- 不处理会发生什么，问题是否值得现在解决。

### 追到根本原因

从可观察现象向下追问“什么机制直接产生了它”，直到找到能被当前改动影响、且有证据支持的原因。

- 对异常修复，恢复从入口、客户端、服务、规则与权限、数据存储、异步任务到外部依赖的实际链路；只检查本次事实涉及的层级，不在页面或报错点提前停止。
- 对新需求，追到用户目标与现有流程之间的断点。
- 对重构，追到真实维护成本、失败模式或交付阻力。
- 只能说明相关性时，写“尚未确认根因”，并给出最小验证动作。

根因要落到具体机制；“体验不好”“架构不合理”“历史原因”“框架就是这样”都还没到根因。

### 界定范围和完成标准

- 写清最小可交付结果，以及明确不做什么。
- 写清受影响的角色与入口，以及实际涉及的客户端、服务、规则与权限、数据、任务、脚本、外部依赖和回归路径。
- 完成标准必须能通过测试、观察或数据核对验证。

### 探索实现影响

需要分析代码时：

1. 用多个关键词定位入口、调用方、写入方和相似实现。
2. 沿实际链路追踪到具体文件和关键行，覆盖本次涉及的客户端、服务端、数据层、任务或交付配置。
3. 记录可复用实现、直接影响和间接风险。
4. 只在存在真实取舍时给 2-3 个方案；简单问题直接给推荐做法和一个备选条件。

每个方案使用实际名称，说明如何处理根本原因、代价、风险和适用条件。工作量使用有依据的时间范围，不用 `S/M/L/XL`。

## 定稿前自己攻一遍

报告写完先当反对者读一遍，逐条回答，答不上就改报告而不是改措辞：

- **根因这条，如果成立，同模式的其它代码为什么没出同样的问题？** 说不出来，说明还停在相关性。
- **从用户原话得到的是决定，还是对现状、效果或根因的事实主张？** 明确的目标与范围决定记录来源并沿用；事实主张独立核对，未验证时保留为假设，不把分析建议冒充用户决定。
- **推荐方案解决的是根因，还是最显眼的那个症状？**
- **完成标准现在就能用测试、观察或数据核对来判定吗？** 判定不了的标准等于没有。
- **如果这个需求根本不做，会发生什么？** 答不出实际代价，优先级判断就是空的。

## 输出

对话先给一句结论，再给不超过五条关键依据。需要留档时使用 `assets/templates/analysis-template.md`，按 `.ai-configs/conventions.md` 的 analysis 路径保存。

### 表达规则

通用规则见 `.ai-configs/conventions.md`〈表达与命名〉。本 skill 另外要求：

- 置信度写成“已确认”或“尚待验证”，并紧跟依据；不单独贴 `High/Medium/Low` 标签。
- 工作量写有依据的时间范围，不用 `S/M/L/XL`。
- 代码和既有文档用文件路径、行号和语义标题引用。

需要更多诊断技巧时，读 `references/req-analyze-guide.md`。用户带着解法来、底层诉求说不清时，读 `references/first-principles.md`。
