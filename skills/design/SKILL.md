# 产品与交互设计

设计要处理真实用户阻力，并让开发和测试无需猜测。只写影响行为、布局和状态的决策。

授权按 `.ai-configs/conventions.md`〈授权、实现判断与验证〉；工程约束按 skill 安装目录里的 `create-plan/references/engineering-checks.md`。

## 开始前

1. 按 `.ai-configs/conventions.md` 读取项目上下文和相关分析、需求、设计产物；已有 design 中的技术契约和已确认决定是本次设计输入。
2. 读取现有页面、组件库版本和设计约束，确认可复用模式。
3. 写清用户问题、根本原因、设计目标和明确边界。
4. 角色、入口、主任务或关键规则存在不同理解时，先自行查证；仍会改变设计结果时，仅暂停依赖该决定的设计内容并向用户确认，继续独立部分。
5. 关键交互决定标明来源及适用边界，区分已确认决定、现状事实、设计建议和基于假设的内容。设计稿存在、保存或格式完整不代表其中建议全部获认可；已有有效决定直接沿用，不新增逐阶段审批。

角色、操作名或状态名称会改变用户行为时，调用 Skill 工具（参数为 `domain-terms`）核对含义，把适用含义落实到入口、动作与反馈。

## 设计

- **信息结构**：用户从哪里进入，先看到什么，如何找到目标内容。
- **主流程**：用户动作、系统反馈、状态变化和下一步。
- **边界状态**：加载、空数据、错误、无权限、极端数据、重复操作和恢复。
- **界面规则**：布局、组件、响应式行为、文案和可访问性。
- **操作规则**：可执行动作、禁用条件、二次确认、撤销、重复操作和跨角色衔接。
- **验证方式**：关键行为如何通过原型、人工操作或测试确认。

只在存在真实取舍时比较方案。方案标题使用实际设计方向，不用字母代号。

形成关键流程后核对主入口、主要动作和重要失败状态；已有决策直接沿用，仍有改变信息结构或用户操作的未决事项时按统一规则确认。

## 输出

先给设计结论和最关键的用户流程。需要留档时使用 `assets/templates/design-doc-template.md`，按 `.ai-configs/conventions.md` 的 design 路径保存。本 skill 负责其中的产品与交互内容：先读完整现役文档，只改本次负责的部分；保留技术契约部分和已确认决定，模板只删本次负责部分的无关章节。

### 表达规则

通用规则见 `.ai-configs/conventions.md`〈表达与命名〉。本 skill 另外要求：

- 先写设计结论和它解决的根本问题。
- 编号只表示用户操作顺序，不作为设计项身份。
- 不复制需求背景，不写组件库常识。

## 完成检查

- 入口、动作、反馈、状态、下一步和完成结果是否闭合。
- 主路径、失败路径、权限和恢复是否明确。
- 每个设计决策是否能追溯到用户问题、根本原因或现有约束。
- 开发和测试是否能据此实施和验收。
- 共享 design 中产品交互与技术契约是否仍能对应，保留的技术内容是否可直接用于实施；没有技术设计时不补造该部分。
- **实施的人仍需要决定哪些用户行为**：空态和超长怎么显示、错误提示写什么、禁用的判定条件、加载与失败的过渡——沿用已确认设计和现有契约；影响用户操作的未决事项按统一规则确认，不留给实施者猜测。

需要更多说明时，读 `references/design-doc-guide.md`。
