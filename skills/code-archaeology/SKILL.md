# 读懂既有代码

改一个没写过的系统时，真正卡住人的从来不是语法，是两个问题：**它跑起来到底怎么走**，
和**它当初为什么写成这样**。第二个问题代码本身答不了——代码只记录了发生什么，
没记录为什么。所以这条线得去别处查。

本 skill 只负责搞懂和讲清楚。**不改代码，不落档**，结论直接喂给下游（写计划、审查、修 bug）。

## 先决定追哪条线

| 你想知道的 | 追哪条 |
|---|---|
| 这个请求进来之后经过了什么 / 数据怎么变的 / 为什么没生效 | **how** |
| 这里为什么要加这个判断 / 为什么不用那个方案 / 这个字段是干嘛的 | **why** |
| 我要动这块，但不知道会碰到什么 | **两条都追**，先 how 后 why |

只追一条就够时不要凑另一条。**范围先说清楚**：追哪个入口、到哪儿为止。
说不清范围就先问，别从一个文件开始漫游。

## how：追它运行时怎么走

从**真实入口**出发，不从文件目录出发。入口是路由、事件订阅、定时任务、命令行、页面动作这类
外面能触发的东西。

1. 找到入口，沿调用往下走到真正干活的地方（写库、发消息、调外部、改状态）。
2. 每一跳记下：**谁调的、传了什么、改了什么、失败了会怎样**。
3. 遇到分支就问这个分支什么条件下会走到——说不出条件的分支，说明还没读懂。
4. 走到异步、消息、定时任务、外部服务时**边界要标出来**：那边是另一段旅程，
   要么继续追，要么明确写「本次不追，止于此」。
5. 关键位置随手记 `文件:行号`。**结论里每一句都要能指回某一行**，指不回去的就是推测。

子系统跨了多个目录或服务时，**并行派几个子代理各追一段**，别一个人从头走到尾——
上下文会先被走廊里的无关代码塞满。派发按
`agents/xman-flow/references/subagent-dispatch-protocol.md`，回来的结果自己核一遍位置对不对。

**别做的事**：不要逐个文件通读；不要因为函数名叫 `handleUpdate` 就认定它在更新；
不要把「我以为它会这样」当成读到的结果。

## why：追它当初为什么写成这样

先在**代码里**找答案，找不到再往外查：

```bash
git log -L <起行>,<止行>:<文件>     # 这几行的完整变更史
git log -S '<关键字符串>' --oneline  # 这个字符串是哪次引入的
git blame -w -C <文件>              # 忽略空白和挪动，看真正改它的那次
```

拿到 commit 之后，**commit message 里的单号、链接、人名就是往外查的线索**。

外部证据源看项目实际接了哪些，**不要假设某个平台一定存在**——本机 skill 列表里有的才用，
没有的直接跳过并在结论里写明「这类证据没查到」。

| 想知道 | 去哪查 |
|---|---|
| 这个功能当初是为了解决什么 | 需求单、需求文档 |
| 这个判断是为了修哪个问题 | Bug 单，commit message 里的单号 |
| 当初的设计方案和评审结论 | 知识库或设计文档 |
| 这个接口的字段当初怎么约定的 | 接口文档 |
| 什么行为当初被认定是「对的」 | 测试用例管理平台、仓库里的既有测试 |
| 这个异步/定时逻辑线上实际在跑什么 | MQ 和定时任务的管理平台 |
| 这段代码什么时候上的线、上到哪 | 发布记录 |
| 界面为什么长这样 | 产品稿和设计稿 |

`references/evidence-sources.md` 存在时先读它：里面是当前团队各类证据对应的 skill 名。

**几条同时要查就一起发出去，不要一个查完再查下一个。**

### 查不到的时候

查不到就写查不到。**不允许用「大概是为了兼容老逻辑」「应该是历史遗留」补空**——
这类话读起来像结论，实际是猜，而且下游会当真。

正确写法是：`git log` 显示这行来自 2023-06 的一次大重构，commit message 只写了「重构订单模块」，
没有关联单号，知识库里也没搜到对应文档 —— **所以这行的动机查不到**。

这跟「没有理由」是两回事，别混。

## 讲出来：用大白话复述一遍

查完之后，**用人话把它讲一遍，讲到对方能判断你是不是搞错了**。

这一步不是给人的仪式感，它对你自己也有用：不读代码就自信断言，是模型的常见失败，
而「讲一遍并附上行号」这个动作会逼你回去核对。讲不顺的地方，通常就是你还没读懂的地方。

讲的时候：

- 先给一句话结论，再展开
- 每个关键论断跟一个 `文件:行号` 或一条命令输出
- 事实、推断、没查到，**三类分开说**，不要混在一段里
- 不要复述代码（「这里调用了 X 方法」不是理解），要说**它导致了什么**
- 对方一旦纠正你，回去重查，不要辩护

## 输出

对话里给，不落档：

1. **一句话结论**——这段代码在干什么 / 它当初为什么这样。
2. **怎么走的**（追了 how）：入口 → 关键几跳 → 落到哪，每跳带位置。
3. **为什么**（追了 why）：证据 + 出处；查不到的单独列出来。
4. **对你要做的事意味着什么**：会碰到哪些地方、哪里不能动、哪里还不清楚。

不写背景铺垫，不写「本次分析涵盖以下方面」。下游要的是能用的理解，不是一份报告。

### 表达规则

通用规则见 `.ai-configs/conventions.md`〈表达与命名〉。本 skill 另外要求：

- 位置写 `文件:行号`，不写「在那个 service 里」。
- 「查到的」和「推出来的」必须分开，推断要写清从哪条事实推的。
- 不用「应该、大概、可能是历史原因」代替查证结果。

## 完成检查

- 结论里每一句能不能指回一个位置或一条命令输出？
- 分支、失败路径、异步边界有没有交代，还是只走了主路径？
- why 查不到的部分，是否明确写了「查不到」，而不是编了一个理由？
- 讲出来的版本，一个没读过这段代码的人能不能听懂并质疑你？
