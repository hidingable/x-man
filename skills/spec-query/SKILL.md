# Spec 查询

按目标路径找到适用的项目规范，读取已登记的事实源，输出「路径 → Spec → 来源」对照结果。
这是轻量防遗漏机制，不是脚本、Hook、CI 校验器或安全门禁。

## 确定查询目标

目标路径来自当前任务：

- 用户明确给出文件或目录时，使用这些路径。
- create-plan 调用时，使用已成型任务的预计修改路径。
- code-by-plan 单独调用、计划未对账或新增路径时，使用当前实际修改路径；已有效对账的部分复用。
- review 调用时，必须先独立理解 diff，再使用 diff 中的实际变更路径。

将目标转换为相对项目根的 POSIX 路径，路径分隔符统一为 `/`，并保持首次出现顺序去重。
任何目标位于项目之外时停止，不尝试用文本前缀猜测。无法从当前任务确定路径时，先向调用者索取路径。

## 优先使用确定性查询

先定位当前项目根和索引。索引不存在时返回「项目未启用 Spec」。项目已有可运行的 xman CLI 时，由助手运行 `xman spec match <目标路径> --json --project <项目根>`，读取命中规范的 source；母仓自身可用 `./xman`。采用当前项目提供的 CLI，不假定用户安装了全局命令，也不为了查询安装运行时。

逐路径保留查询结果，同一 source 只读一次；命令会校验索引和匹配关系，成功后无需再让模型重复计算 glob。非法索引、来源不可读或命令执行失败时标记「Spec 未完成对账」，不能用后备方式把错误改成无命中。工具不可用时才采用下方人工匹配，并注明方法；需要的只读校验由助手执行，不默认让用户运行。

## CLI 不可用时读取并校验索引

按 `.ai-configs/conventions.md` 的 Spec 查询约定定位索引。约定不可用时，兼容查找项目根的
`.ai-configs/specs/index.json`：

- 索引不存在：返回「项目未启用 Spec」，不将它报成错误。
- 索引存在：完整读取后再匹配，不用 `rg` 片段或搜索摘要代替 JSON 结构。

匹配前确认：

- 根对象的 `version` 为 `1`，`specs` 为数组。
- 每条 `id` 唯一且匹配 `[a-z0-9-]+`。
- `source`、`description` 非空，`paths` 是非空字符串数组。
- `source` 是项目内存在的 UTF-8 普通文件。
- pattern 不是绝对路径，不包含 `..`、反斜杠、`[]`、`{}` 或 `***`。

任一项非法时报告精确 spec id / 字段和原因，整次查询标记为「未完成」。
不用其余合法条目生成一份看似完整的部分结果。

## CLI 不可用时按路径匹配

每个 pattern 必须匹配完整目标路径，语义与项目 Spec 核心一致：

- `*`：匹配零个或多个非 `/` 字符。
- `?`：匹配一个非 `/` 字符。
- `**/`：匹配零个或多个完整路径段，因此 `src/**/a.py` 同时匹配 `src/a.py` 和 `src/x/a.py`。
- 其他位置的 `**`：可跨 `/` 匹配任意字符。
- 其他字符按字面量匹配。

对每个目标收集全部命中项，按 spec id 排序。同一 Spec 命中多个目标时只读一次 `source`，
但在对照结果中保留每个目标的命中关系。无法确定某个 pattern 的语义时，将它报为「待确认匹配」，
不得降级为无命中。

## 读取事实源

完整读取每个命中 Spec 的 `source`。规范正文是事实源，`description` 只是适用原因，不能用它代替正文。
该查询只提供规范证据；如果规范与当前用户裁决、PRD、契约或已验证代码事实冲突，
列出冲突的两个事实源交给调用者裁决，不自行判定 Spec 永远优先。

## 输出

直接查询时输出简洁对照表：

| 目标路径 | Spec ID | 事实源 | 适用原因 |
|----------|---------|----------|----------|
| `path/to/file` | `spec-id` | `path/to/source.md` | description |

然后列出：

- **已读取规范**：本次实际读取的 source；不复制整篇正文。
- **未命中路径**：确定没有匹配项的目标。
- **未完成 / 冲突**：索引非法、匹配不确定、来源不可读或事实源冲突；没有则删除。

被 create-plan 或 review 调用时，返回同样的映射与冲突，由调用者写入自己的计划或审查结果；
本 skill 不另建产物文件。

被实施 skill 调用时沿用同样输出。调用方按 skill 安装目录里的 `create-plan/references/engineering-checks.md`核对领域、设计、utils 和组件的实际适用规则；记录相关条款对任务的约束及验证，不复制完整规范，也不把通用检查示例当作项目已采用规则。

## 边界

- 只读：不修改 `index.json`、规范正文、计划、代码、缓存或 Git 状态。
- CLI 成功只证明索引与匹配结果；人工匹配注明限制。两者均不证明业务规则已获确认或实现符合规范，不代替审查、测试或真实用户路径验证。
- 不扩展 glob 语法：只理解上述 `*` / `**` / `?` 子集。

## 各阶段什么时候查、怎么记录

项目可选用 `.ai-configs/specs/index.json` 登记「现有规范事实源约束哪些项目路径」。
索引只保存 `id`、`source`、`description` 和 `paths`，不复制规范正文。

需要确认某些路径适用哪些规范时，调用本 skill：

- create-plan 在任务的预计修改路径成型后查询，把命中规范记入〈实施依据与边界〉。
- code-by-plan 单独调用时核对当前修改路径的规范；有计划时核对其引用的 source 和约束是否仍有效。新增路径或规范变化时只补查受影响部分，不机械重查全部任务。
- review 先只读 diff 建立独立理解，再用实际变更路径查询，将规范作为验收证据源之一。
- 其他 skill 只在已知目标路径时查询，不为了匹配 Spec 猜测修改范围。

索引不存在表示项目未启用 Spec，可正常跳过。索引存在但非法、来源不可读、
匹配不确定或 `spec-query` 不可用时，必须标记「Spec 未完成对账」，不得写成「无命中」。
规范与当前用户裁决、PRD、契约或已验证代码事实冲突时，列出冲突交由用户裁决，不默认 Spec 永远优先。

可运行项目已有的 `xman spec match <路径> --json --project <项目根>` 时，优先使用其确定性匹配结果，再读取命中的 source；CLI 不可用时按 `spec-query` 的匹配规则查找并注明采用了人工匹配。索引或命令报错不等于 CLI 不可用，不得用人工匹配把非法索引解释为无命中。只读校验由助手在授权范围内运行，不默认交给用户执行。

计划和实施记录对相关规范写清「source 与适用条款 → 当前任务受到的约束 → 验证方式」，而不只列规范名称。Spec Hook 的读取记录仅证明正文已交付，不证明实现符合要求；审查和验证仍需对账。规范读取本身不扩大修改范围，也不授权改写规范。
