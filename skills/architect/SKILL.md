# 技术架构

这个 skill 只管一件事：**在写实现之前，把接口长什么样定下来。**

不是画架构图，不是写一份「方案文档」。产出是**能编译的骨架**——类型定义、函数签名、
调用点长什么样——实现体先空着。骨架对了，实现是填空；骨架错了，实现写得再漂亮也是白写。

授权按 `.ai-configs/conventions.md`〈授权、实现判断与验证〉执行；阶段选择与已有证据复用按 `.ai-configs/conventions.md`〈阶段职责与证据复用〉执行。

## 什么时候用

| 用 | 不用 |
|---|---|
| 新子系统，别的模块要依赖它 | 改一个函数内部逻辑 |
| 公共契约要变（接口、事件、表结构） | 加一个字段、改一处文案 |
| 要给别人用的包或工具 | 已经有明确方案，只差实施（用 `create-plan`） |
| 重构会波及一片调用方 | 界面怎么摆、用户怎么走（用 `design`） |

**小改动别用这个。** 三步竞技场的成本只有在「选错了要返工很久」的时候才划算。

## 一、先接地

不了解现状就设计，设计出来的东西会跟已有的东西打架。

调 `code-archaeology`：`how` 搞清现在这块怎么跑的，`why` 搞清当初为什么这么定。
**重点是找出约束**——哪些调用方不能动、哪个契约对外承诺过、哪些数据已经落库改不了。

接地的产出是一段简短的**约束清单**，后面每个候选设计都拿同一份清单去做，不许各做各的。

读取同任务已有 design，把产品交互和已确认决定纳入约束。状态、角色或公共接口名称会影响契约时，调用 Skill 工具（参数为 `domain-terms`）核对含义，将含义与适用边界写入类型和调用示例。

需要比较接口负担、复杂度归属或替换点时，读 skill 安装目录里的
`create-plan/references/module-design.md`。用其中的术语和 deletion test
解释设计取舍；项目已有清楚含义的 API、service、component 等名称照常使用，不为统一词表改名。

## 二、出候选：从调用点倒推

**先写「用起来长什么样」，再写签名，最后才写实现。**

这个顺序不能反。先写实现再补接口，接口会长成实现的形状，而不是使用者需要的形状。

每个候选交四样，缺一不可：

1. **调用点草图** — 使用者的代码长什么样。假装这个东西已经做好了，把调用代码写出来。
2. **核心类型定义** — 数据结构、状态、错误类型。
3. **公开函数签名** — 只有签名，实现体空着或 `TODO`。
4. **一句话理由** — 为什么是这个形状，它把什么难题挡在了使用者外面。

### 并行出，不要串行改

**同时派 2-3 个子代理各做一个候选，互相看不见对方的方案**，
按 `agents/xman-flow/references/subagent-dispatch-protocol.md` 派发。
串行做出来的第二个方案，永远是第一个方案的微调——你已经被自己锚定了。

子代理只返回自己负责的章节或附属稿，由指定整合者合并，不同时直写共享 design 主文件。

默认继承会话模型，用独立上下文和不同设计机制形成候选；用户指定或实际需要模型对照时再换模型。仅换模型不能证明方案独立。

### 每个候选自检两件事

- **接口深度**：使用者要知道多少东西才能用对？要传五个参数、还要记得先调初始化、
  还要自己处理三种错误——这是浅接口，难用的部分被推给了使用者。
- **调用方能不能用对**：在独立上下文中依据签名编写调用样例，检查能否编译或运行，
  以及错误路径是否清楚。不靠作者解释内部步骤才能用对，验证未执行时明确说明。

## 三、交叉评判

在独立上下文中按同一约束和调用证据交叉评判，默认继承会话模型。选择理由必须能被证据检验，不因模型不同就认定评判可靠。

评判标准提前写死，不要临场发挥：

- 调用点代码哪个最短、最难写错？
- 哪个把最多的复杂度挡在了使用者外面？
- 哪个在约束清单上没有硬伤？
- 哪个错了以后最好改？（**这条常被忽略，但最值钱**）

评判要给的是**选哪个 + 为什么 + 被淘汰的方案里有什么值得吸收**，
不是给三个方案打个分了事。

## 四、照骨架实现

把签名里的空实现换成真逻辑。这一步唯一的纪律是：

**发现骨架不够用时，必须停下来说，不许偷偷改签名。**

具体就是这三条——出现任何一条，说明骨架错了：

1. 同一个绕法出现在**互不相关**的调用点；
2. 类型需要 `any`、强制转换、忽略类型检查的注解才能过；
3. 某个函数需要当初签名里没有的参数或额外状态。

（这三条和 `review` 的〈结构信号〉是同一套判据。设计阶段用来止损，审查阶段用来兜底。）

## 五、错了就报废

上面三条出现之后，正确做法是**把骨架整个丢掉重来**，不是在错的骨架上打补丁。

这一步最难，因为骨架已经花了力气。但错误的结构会一直收利息：
每个后来的人都要绕一次，每次绕都让下一次更难改。**现在丢掉是最便宜的时候。**

重来时带上这次学到的东西——通常第二版会好很多，因为你已经知道哪里会崩。

## 输出

先在对话里给：

1. **选了哪个** —— 一句话说清它的形状。
2. **调用点长什么样** —— 贴那段代码，这是最有说服力的部分。
3. **为什么不是另外几个** —— 每个一句话。
4. **接地时发现的硬约束** —— 哪些东西不能动。

需要留档时按 `.ai-configs/conventions.md` 的 design 路径保存。本 skill 负责其中的技术契约内容：先读完整现役文档，只改本次负责的部分，保留产品与交互部分和已确认决定。
文件里额外保留完整的类型定义和签名。**被淘汰的候选也写进去**——
半年后有人问「为什么不用 X 方案」，这段就是答案。

### 表达规则

通用规则见 `.ai-configs/conventions.md`〈表达与命名〉。本 skill 另外要求：

- 候选用它实际的形状命名（「按事件流拆」「单一门面」），不用「方案 A / B / C」。
- 贴代码，不要用散文描述代码长什么样。
- 「这个更优雅」不是理由。理由要落在：调用点更短、更难用错、错了更好改、约束上没硬伤。

## 完成检查

- 调用点草图是不是真的写出来了，而不是只描述了一下？
- 候选是不是独立提出了不同设计机制，而非只做串行微调？
- 评判是否使用独立上下文、同一约束和实际调用验证？
- 接地时的约束清单，选中的方案逐条对得上吗？
- 共享 design 中技术契约是否与产品交互一致，两部分是否仍可直接指导实施；没有产品设计时不补造该部分。
- 实现时如果发现要给签名加参数，你会停下来说，还是会顺手加上？
