# 流程复盘

复盘要回答的只有一个问题：**这次哪里多付了代价，下次能不能提前拦住。**

只写付出过代价的环节：不打分，不填固定格子，不总结做得好的地方。

用户只是当场指出一次具体失误、要求记下来时，不用做整轮复盘：读 `references/mistake-record.md`，按它记一条事件。

## 先建证据，再回忆

结论来自实际记录。按 `.ai-configs/conventions.md` 找到本次任务的产物，从里面捞事实：

- progress 产物 — 哪一步做了两遍，哪一步的实际耗时和计划差得远
- harness 产物和完成声明核对记录 — 哪些问题是验证阶段才发现的
- review 结论 — 哪些问题本该在写代码时就避免
- decisions 产物 — 哪些决策后来被推翻
- 对话本身 — 用户在哪里打断、纠正或重复解释了同一件事

用户的纠正是最强的信号：**同一件事被解释两次，就是一次流程失败**，不管最后结果对不对。

记录不足时说明缺什么，缺的部分保持空白。

## 只写有代价的条目

每条复盘发现必须写清代价，格式是「哪一步 → 发生了什么 → 多付了什么」：

- 多做了一轮实现或推翻重来
- 问题拖到更贵的阶段才暴露（写代码时能发现的，拖到验证或审查）
- 用户被迫做了本可以避免的确认或纠正
- 交付时间或范围因此变化

说不出代价的不是发现，删掉。只有态度、没有动作的话（「下次更仔细」）同样删掉。

## 判断是不是流程问题

对每条有代价的发现问三句，三句都过才升级成规则：

1. **以前发生过吗？** 在既往 lessons 和 `.ai-configs/evolution/` 里搜一次同类问题。第一次发生就先记为一次性。
2. **换个人、换个模型会不会照样发生？** 只在这次特定上下文里成立的，是偶发；换谁来都会踩的，是流程问题。
3. **说得出一个能提前拦住它的具体动作吗？** 拦截动作必须落到某个 skill 的某一步、某条检查或某个前置确认上。说不出具体动作的，说明还没找到真正原因，回上一步继续查。

三句过不了就如实写成一次性观察，不升级。**把偶发噪音写成长期规则的代价是永久的**——它会在之后每一次流程里消耗预算。

## 拦截动作落在哪

按下面几类找能提前拦住问题的地方，从上往下优先：

| 类别 | 什么时候看 | 拦截动作的样子 |
|---|---|---|
| 自动检查 | agent 犯了一个 lint、类型检查、测试或文件位置检查本可以抓到的错；或者项目根本没有 pre-commit 和 CI | 先看项目已有的检查命令和 CI 是否接上、是否真的在跑；机械性的问题（固定写法、禁用 API、导入形状、文件位置）做成检查，比写成规则可靠 |
| 导航 | 找一个文件或一条信息花了很长时间 | 在入口文档里加一行指向，写清什么情况下去哪里找 |
| 规范 | 审查没抓到一个需要判断的问题 | 给项目规范加一条或改清楚一条；只有需要判断的才进规范，机械性的回到上一行 |
| 指令文件 | AGENTS.md、CLAUDE.md、skill 太长，或者有些规则从没改变过行为 | 删掉无效句，能做成检查的挪去做检查 |
| 工具开销 | 某次工具调用特别贵，或某个脚本、MCP 输出冗长 | 换成更省的调用，或给脚本加 `--json`、加过滤参数 |
| 信息获取 | 关键信息 agent 拿不到，只能问人 | 让它能读到：服务日志、只读的第三方账号、文档链接 |

## 输出

只写实际存在的内容，空的分组直接不出现：

1. **这次的实际路径**：走了哪些阶段，跳过了什么，为什么。一句话。
2. **付出代价的地方**：每条按「哪一步 → 发生了什么 → 多付了什么」写，附证据位置。
3. **判定为流程问题的**：连同三问的回答，和那个具体的拦截动作。
4. **记为一次性的**：一句话带过，说明为什么不升级。
5. **本次没有值得沉淀的**：如果确实如此，就这么写，这是合法结论。

每类最多五条。超过时合并同类，优先保留代价最高的。

按 `.ai-configs/conventions.md` 的 lessons 路径保存。

样例：

```text
实际路径：需求分析 → 计划 → 实施 → 验证 → 审查，跳过了设计（改的是已有页面的
        取数逻辑，没有新界面）。

付出代价的地方：
- 计划阶段 → 只找到 RenewalService 一个状态读取方，实施时才发现另外两个
  （jobs/expire_notify.go、report/weekly.go）→ 实施中途改了一次计划，多花约 40 分钟。
  证据：本次 progress 产物的第二次更新
- 验证阶段 → 过期合同分支没有测试，靠手工点出来 → 问题拖到验证才暴露。
  证据：本次 harness 报告「未满足的结果」第一条

判定为流程问题：
- 「计划阶段只搜到一个调用方就开工」。以前发生过（`.ai-configs/evolution/` 里 2026-06
  有一条同类）；换谁来都会踩，因为单次 grep 命中一个结果时没有强制继续找的动作；
  拦截动作：create-plan 的「开始前」第 4 步已要求搜全部读写方，但没有要求写进计划文件
  的「同步修改」栏 —— 补上这条即可在计划评审时看出遗漏。

记为一次性：
- 本地缺 wkhtmltopdf 导致一条测试 skip。环境问题，不进规则。
```

## 反模式

| 反模式 | 症状 | 纠正 |
|---|---|---|
| 填格子 | 为了让“做对了什么”不空而编内容 | 空的分组直接删掉 |
| 空话教训 | “下次更仔细”“沟通要更早” | 没有具体拦截动作就不是教训 |
| 噪音升级 | 一次环境故障写成长期规则 | 过三问，过不了就记一次性 |
| 流水账 | 逐阶段复述做了什么 | 只写付出代价的地方 |
| 表扬环节 | 总结做得好的地方 | 删掉，复盘不产出正向评价 |
| 无证据断言 | “感觉这次计划质量不高” | 指出具体哪一步、代价多少、证据在哪 |

## 结束动作

有条目通过三问时，读 `references/mistake-record.md`，按它把那个具体的拦截动作写成一条模式规则（记动作，不记现象）。没有通过的，不写、不凑。

表达和命名按 `.ai-configs/conventions.md`〈表达与命名〉执行，核心一条：阶段和问题用实际名称，不用「第 3 阶段」「问题 2」这类代号。
