# 解决 Git 冲突

以真实 Git 状态确定正在整合的变更，保留双方仍有效的目标。解决冲突的证据包括行为正确和改动范围正确；删除冲突标记只是其中一个检查。

## 识别操作与保护已有工作

1. 读取 `git status`、当前 HEAD、未合并索引、暂存差异和未暂存差异。按 [Git 状态与三方内容](references/git-conflict-states.md) 判断是 merge、rebase 还是 cherry-pick，并记录涉及的提交；不凭分支名或冲突标记判断操作。
2. 建立本次冲突文件清单，保留当前 staged、unstaged、untracked 状态的记录，区分操作自动合并的内容与用户无关改动。来源无法确定的差异先保留，不自动归入本次提交。
3. 读取当前用户授权，确定本次要做到编辑、暂存，还是完成整个 Git 操作。已经授权完成 merge、rebase 或 cherry-pick 时，后续必要的暂存与继续操作沿用该授权；仅要求分析或修好文件时，不擅自扩大到提交。

不使用全仓 `reset`、`restore`、`clean` 或自动 stash 来清空现场。覆盖、删除或中止会影响用户未保存内容时，先保留可恢复副本并说明具体影响；只有相应操作已获授权时才执行。用户要求中止，或方向需要重新选择时，可以采用该操作对应的 `--abort`，不承诺它在所有脏工作区都能无损恢复。

## 读取双方意图并解决具体冲突

1. 对每个冲突读取索引 stage 1 的共同基线、stage 2 的 ours、stage 3 的 theirs，以及完整函数、调用方和相关测试。新增、删除、重命名等冲突可能缺少某个 stage，按索引实际内容处理，不能把缺失当作读取失败后取另一侧的理由。
2. 查双方相对基线的改动、提交说明、相关历史与已提供的需求或 issue。写清双方分别要改变什么以及依据；读不到历史意图就标明证据缺口，不用代码外观补故事。
3. 合并能同时成立的意图，只调整维持这些行为所需的冲突及直接受影响代码。不要统一选择整份 ours/theirs，不趁机重构，也不创造双方都未要求的新行为。重命名、删除、二进制或生成文件的处理按参考中的语义检查执行。
4. 双方目标互斥或唯一正确做法没有证据时，停在该处语义冲突：列出冲突行为、依据、选项的实际后果，向能作决定的人询问。独立且已明确的冲突可以继续处理；未决项保持未解决状态，不能通过暂存让 Git 误以为已有裁决。

`ours` / `theirs` 是当前索引的角色。尤其在 rebase 中，ours 通常是目标基线加已重放的结果，theirs 是正在重放的提交；它们不等同于用户口中的“我的分支”和“别人的分支”。每次继续后发生新冲突，都重新核对当前提交与三方内容。

## 验证行为和暂存范围

1. 检查冲突范围内的标记、语法和格式；再运行能覆盖双方预期行为的现有测试或针对性验证，并检查自动合并的相关代码是否产生接口或调用错配。验证范围按项目规则与实际风险选择，不把全仓测试当成固定前置。
2. 暂存需要在已有授权范围内逐路径执行。整文件暂存会带入该文件的全部工作区内容；同文件存在无关改动时，先确认能否安全分离，无法分离则保留现场并说明阻塞，不用 `git add .`、`git add -A` 或 `commit -a`。
3. 核对 `git diff --cached` 的内容与预期结果，复核未合并索引和无关路径的原有状态。工作区测试通过不代表暂存内容一致；两者不一致时，必须验证实际将提交的内容。

无关改动即使此前已经 staged，也不能随继续操作被提交。若当前索引混有这类内容，先停在 continue/commit 之前，说明需要怎样隔离；未经授权不取消别人的暂存、不把无关内容收入提交。

## 按授权结束当前操作

- 只要求修文件：报告已解决的行为、验证结果、仍未合并的索引或尚未暂存的文件。
- 已授权完成操作：所有语义冲突有结论、暂存范围正确、必要验证通过后，使用当前操作对应的 `--continue` 或 merge 提交入口；后续再遇冲突时重复三方核对。不得自动 `--skip` 丢掉提交，测试失败也不能靠忽略失败来继续。
- 中止、权限不足或语义待定：保留已完成工作和现场，明确当前停止点、尚缺的决定及下一步。解决冲突不自动包含 push、发布或强制改写远端。

交付时简述“操作及提交 → 双方保留的行为 → 验证 → 暂存/继续/提交状态 → 待裁决项”。需要留档时遵循用户指定位置或 `.ai-configs/conventions.md` 中适用的产物约定。
