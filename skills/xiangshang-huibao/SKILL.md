# 向上汇报：起草、体检与改写

## 这个技能在解决什么问题

绝大多数中层的汇报停在"告知"：做了什么、做到什么程度、遇到什么问题。老板听完知道了，然后还得自己判断、自己决策、自己想办法——问题被扔回给了他。

好的汇报是**交付判断**：不仅说发生了什么，还说接下来会怎样、现在该做什么决策、需要什么支持。老板只需要做一个动作——点头。

每一次输出都要通过同一个检验：**老板读完，是否可以只回一个"好"就结束？** 如果他还得追问"那怎么办"，这份稿子就没写完。

---

## 第 0 步：动笔前把三件事定死

这三件事定错，后面写得再好也白写。能从上下文判断就直接判断，判断不了就用 `ask_user_input_v0` 一次性问完，不要逐个追问。

### 1. 模式

| 信号 | 模式 |
|---|---|
| 给的是原始素材、进展、数据、一堆待办 | **起草** |
| 给的是写好的稿子/一段话，问"行不行""帮我改""优化一下" | **体检 + 改写** |
| 给了稿子又要求补充新内容 | 先体检，再基于诊断重写 |

### 2. 载体

**载体不是默认 Markdown。** 汇报的真实载体决定了交付方式，判错会白做一轮：

| 用户给的 / 要的 | 交付方式 |
|---|---|
| 上传了 .docx / .pptx / .xlsx，要求"改" | **在原文件上改**，保留格式与图表，见"最小破坏改写" |
| 没有原件，要正式书面稿 | 写 Markdown 文件到 `/mnt/user-data/outputs/`，并说明可转 docx |
| 要发 IM / 邮件 / 微信给领导 | 直接在对话里给可复制的纯文本，不写文件，控制在手机三屏内 |
| 要口头汇报、会上发言 | 给发言脚本：开场结论 30 秒、主体 3 分钟、收口提问预案 |

拿不准时按用户给的原件格式走——用户给 docx 就还 docx。

### 3. 受众与目的

- 汇报给谁：直属上级、跨部门、还是老板的老板？层级越高，明细越要下沉。
- 这次要什么：**同步进展 / 要资源 / 报坏消息 / 要拍板**。目的决定结论那句话怎么写。
- 是否会被转呈或分发？会，则**必须无人称**（见下）。

## 起草流程

### 第 1 步：判定层级，并把它推到决策层

| 层级 | 识别特征 | 价值 |
|---|---|---|
| **事实层** | 通篇"已上线""已完成""覆盖 X 个区域"；动词都是过去式；读完不知道下一步 | 老板看周报也知道，不创造价值 |
| **分析层** | 出现"原因是""经分析""导致"；有归因但归因后没有动作 | 老板开始觉得你有脑子 |
| **决策层** | 出现明确取舍、优先级、时间点、资源量；有"建议 X，不做 Y"和"若 A 则 B" | 老板只需说"好"或"不好" |

还有一种更差的形态要专门识别——**提问层**：稿子里出现"是否还要做 X？""要做的话做哪些呢？"。这不是谦虚，是把年度决策原样退回给老板。见到问句，一律改写成带依据的建议。

**成稿必须落在决策层。**素材只够写到事实层或分析层时，不要编一个判断糊上去（编造的判断会害了用户）。做两件事：

1. 从已有数据能推出的判断，推出来，并在稿中标明推理依据；
2. 推不出来的，收尾时列成"待补数据/待确认判断"，交还用户。

### 第 2 步：盘点缺口，最多问 3 个

对着下面几项看素材缺什么，**只问真正卡住成稿的**：

- 结论是什么？这次要让老板带走的一句话
- 有没有硬数据？（有形容词无数字的地方最需要补）
- 需不需要老板做决定、给资源？具体给什么、给多少
- 有没有坏消息被藏着？

素材够就别问，直接写。

### 第 3 步：按黄金结构成文

三明治：**结论 → 证据 → 带底气的判断**。

```markdown
# [一句话结论式标题]

## 结论
[一句话。不铺垫、不背景、不"先简单介绍一下"。
 开头 30 秒就让老板知道要说什么。]

## 支撑数据
[3-5 条。每条都是数字或事实，不是形容词。
 "客户很满意" → 无效；"续费率从 80% 涨到 92%" → 有效。]

## 判断与推演
[回到结论再说一遍，这次带推演：
 X 不做，下个月会怎样；做了，预计到什么水平。]

## 建议动作
[具体到人、量、时间。"增加人手" → 无效；
 "B 环节人手加到 3 人，C 环节提前一周启动" → 有效。]

## 待决事项
[需要拍板什么、需要什么资源，写清楚。
 不需要就写"暂无，按上述方案推进"，但别把真需要的资源咽回去。]
```

不同场景对这个骨架有增删，写之前读 `references/changjing.md` 对应那一节。

### 第 4 步：翻译成老板的语言

通读一遍，把"你的语言"换成"他的语言"。他关心五件事：**目标、进度、风险、资源、竞品**。

- "优化了代码" → 他不懂
- "系统响应时间从 3 秒降到 0.5 秒，用户投诉率下降 40%" → 他懂了

**竞品是最常被漏掉的那一件。** 涉及做不做、先做哪个的判断，只有内部数据不足以支撑——老板问的第一个问题往往是"同区域竞品有没有"，而不是"我们这儿量有多大"。没有这一列，整份候选项表的准入依据就只剩自说自话。适用于产研规划、需求评审、市场类汇报；纯成本治理与稳定性事项不适用。

替换句式见 `references/cihui.md`。老板个人的具体判据见 `references/laoban-panju.md`——先读那一份，再动笔。

### 第 5 步：数据自检 + 体检清单，然后交付

见下面两节。交付后在对话里只留一小段说明：结论是什么、替用户做了哪些判断、哪几处需要用户自己确认。**不要把整篇稿子在对话里再抄一遍。**

## 体检与改写流程

用户拿来一份稿子时按此顺序做。**只诊断不改写等于把问题扔回给用户**，最后一定要给改写件。

1. **定层级**——事实层、分析层、决策层还是提问层？直接说，别绕。
2. **扫四条禁忌**（下表）。
3. **挑形容词**——把"很好、不错、明显提升、基本完成"逐条列出，标注这里应该填什么数字。填不上的，就是用户还没查清的地方。
4. **数据自检四查**（见下）。这一步最容易被跳过，也最容易在会上翻车。
5. **给改写件**——按黄金结构重排，按"最小破坏"规则落到正确载体上。诊断放对话里（简短），改写件放文件里。

### 四条禁忌

| 禁忌 | 长什么样 | 为什么致命 |
|---|---|---|
| **只报问题不给方案** | "项目出问题了""还在想""是否要做 X？" | 等于告诉老板"我搞不定，你来"。哪怕建议不成熟也要给——给了他能帮你改，什么都不给他不知道从哪帮起。**候选项越多越要给建议**：规划类稿子天然面对一堆待选项，写的人下意识把选择题交出去，这正是提问层的高发区 |
| **模糊词** | 大概、可能、差不多、初步考虑、猜测、争取、后续考虑 | 信任粉碎机。"大概完成 80%"，老板听到的是"你没有准确数据"。不确定留在自己肚子里，站到老板面前时要是确定的。**处置不是改词**——把"猜测"换成"初步判断"一分不得，模糊的根因是没去现场。要么补调研，要么明写"归因未完成 + 核查交付时间" |
| **瞒坏消息** | 风险写在第 7 段的小字里、藏在括号中 | 坏消息不会因为藏着变好，只会在老板最不希望的时候炸。要第二时间说，带原因和补救方案说 |
| **让老板猜** | 通篇专业黑话、没有结论 | 不是表达能力问题，是没翻译。只说目标、进度、风险、资源这四样 |

详细评分卡见 `references/tijian.md`，可直接输出给用户。

### 坏消息必须写成三元组

每一条坏消息都要凑齐 **坏消息 → 事实（带数字）→ 处置建议**。缺处置的不许写进稿子，只有前两项等于报警不救火。长稿里把坏消息集中成一张表放在结论区，不要散落在各章节的括号里。

## 无人称写作规范

汇报稿是组织文书，不是个人陈述。稿子一旦被转呈、分发、贴进纪要，第一人称就会失效或走样。**判断本身就带署名，"我"是冗余的。**

**规则：正文不出现"我""我们""咱们""笔者"。**用无主语祈使句、判断句、被动结构替代。

| 别写 | 写成 |
|---|---|
| 我认为增长引擎已经换挡 | 增长引擎已经换挡 |
| 我建议尽快推进 | 建议 2027 年 Q1 启动 |
| 我们做了三件事 | 本期完成三件事 / 已完成三件事 |
| 我会在 9 月底前补上测算 | 收入测算于 9 月底前补齐 |
| 我的判断是 A 方案更优 | 判断：A 方案更优，依据如下 |
| 我需要您支持 | 待决事项 / 需要拍板的三件事 |
| 我们遇到了困难 | 当前卡点：XXX（附处置建议） |

**例外**：口头发言脚本可以保留"我"，因为发言人在场；IM 短消息可以保留，因为是对话。书面稿一律无人称。

**姿态同时要不卑不亢**：不要"打扰您""还请多多指正""如有不妥请批评"这类下跪式表达，也不要"必须立刻""只能这么做"这种越界口气。用户原稿里有，改掉并说明原因。

## 数据自检四查

交付前必过，四项都查完再输出。这是最容易被跳过、也最容易在会上被抓住的一关。

1. **算一遍倍数与百分比。** "增长了 3 倍"是 4 倍还是 2.9 倍？涨幅、占比、同比全部用原始数字复核一次。原稿算错的，改对并在诊断里点名。
2. **查时间线自洽。** 计划表里的上线时间与正文描述的实际状态是否矛盾（例如表中写"12 月上线"，正文说"已开通 9 个地区"）。这类矛盾自己发现不了，只能靠逐条比对。
3. **查口径一致。** 同一指标在不同章节的分母是否相同；总数与分项之和是否对得上；估算值必须标注"估算，口径待核"，不能混进实测值里。
4. **查空表与空承诺。** 出现"以下为 XX 情况："后面却没有数据的段落，出现"后续考虑优化"却无时间点的动作——这两类是稿子里最显眼的洞，全部列进"待补数据"清单。

## 最小破坏改写

用户说"直接改原文"时，是要**修订**，不是要**重写**。重写会毁掉他花时间做的图表和明细，也让他无法对照检查改了什么。

1. **在原文件上改。** docx 用解压改 `word/document.xml` 再压回的方式（读 `docx` skill），pptx 同理。不要新建一个文件把内容搬过去。
2. **图表、截图、数据表一律保留。** 它们是稿子的证据，改写只动文字与结构。
3. **明细不删，只下沉。** 决策相关内容提到前面，明细、地区清单、原始反馈整体移到附录或保持原位。
4. **就地替换模糊句。** 找到原句改写，不要整段推倒——用户要能一眼看出改了哪里。
5. **新增只加三块**：开篇的结论区、坏消息三元组表、文末的待补数据清单。
6. **改完渲染检查。** 转 PDF 抽查首页、改动章节、末页，确认排版和图表没坏。

用户需要看清改动时，提供 Word 修订痕迹版（`<w:ins>`/`<w:del>`，见 `docx` skill）。

## 长稿分层

年报、述职、经营分析这类长稿（超过 8 页），按这个比例分：

- **首页 = 决策区**：结论、关键数据表、坏消息表、待拍板事项。老板只读这一页就能决策。
- **中段 = 证据区**：分章节的数据与归因，每章开头一句判断，后面才是明细。
- **末段 = 附录区**：地区清单、原始反馈、文档索引、待补数据清单。

判断标准：**把首页遮住，剩下的部分老板读不出结论——说明分层做对了；首页遮住还能读出结论——说明结论没提上来。**

## 频率与心态

**频率不是越多越好，是越准越好。** 看节点不看日历：项目到关键节点、预算快用完、团队有人要离职、老板问了没答上来的问题查清楚了——这些是非汇报不可的时刻。平时每周一次即可；天天汇报，老板不会觉得你靠谱，会觉得你没有独立思考能力。

**姿态**：汇报不是去接受审判，是去帮老板做决定。他焦虑得够多了，他需要的是能给他确定性的人。
