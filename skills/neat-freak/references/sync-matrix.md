# 改动类型对应要查的文档

矩阵用来找该查哪里，不用来强造固定文件名。先认出项目已有的使用说明、架构、运维和决策文档，再把对应内容更新到位；一份文档承担几种职责时就地改，不为形式拆文件。

## 代码改动 → 要查的内容

| 改了什么 | 要查的内容 |
|---|---|
| API、路由、协议 | 接入说明、鉴权、示例、调用方文档、冒烟脚本 |
| 环境变量、外部服务、模型 | 示例 env、运行手册、默认值、下游配置、回退说明 |
| schema、存储字段 | 数据模型说明、迁移与回滚、缓存和派生数据、`.ai-configs/specs/` 里的模块规格 |
| 用户流程、权限、导航 | README 或产品说明、权限说明、操作手册 |
| 服务、部署 | 运维手册、服务名、回滚步骤、上线后的验收方式 |
| 定时任务、告警 | 任务说明、调度配置、失败处理、告警接收人 |
| 退役、改名、下线 | 旧名字在文档、规则文件、skill、记忆里的非历史引用；明确标为历史的证据保留 |
| 命令、脚本、目录结构 | README、规则文件里的命令和路径，`.ai-configs/project-context.md` |

## 常见的过期形态

| 形态 | 处理 |
|---|---|
| 规则文件顶部写着「某日 X 上线，详见 Y」 | 仍有效的约束并进正文；纯历史交给 git |
| 规则文件里抄了完整架构或数据流 | 留约束和指向 docs 的指针，机制说明回 docs |
| 多个版本都自称现役 | 以代码开关和实际运行裁决，旧版本标「已退役」 |
| 已完成的待办仍列为开放项 | 核实后删除 |
| 同一规则复制在多处 | 留一处权威，其余改成指针或删除 |
| 单次事故的长篇经过留在记忆里 | 提炼成可复用的一条，过程交给 git 或事故文档 |

## 规则文件的问题 → 动作

| 发现 | 动作 |
|---|---|
| 引用的路径、命令、服务不存在 | 当前机器能唯一确认时就改；涉及其他机器的路径只报告 |
| 上下级规则互相矛盾 | 项目声明能唯一裁决就合并，否则列为「无法裁决」 |
| 项目声明 `CLAUDE.md` 和 `AGENTS.md` 同源，但软链或导入缺了 | 在授权范围内补上，并确认平台实际加载到 |
| `.gitignore` 缺少规则明文要求的敏感文件模式 | 补上，并检查有没有已经被跟踪的敏感文件 |
| 命名违规、根目录乱放文件 | 只报告；移动、改名、删除列为待确认 |
| 大量「保持整洁」「注意安全」之类没有判据的句子 | 改成能检查的条件，或删掉 |

## 跨项目

共享的 API、SDK、域名、认证、schema、环境变量变了，或者公共脚本、模板被多个项目引用时，搜索实际调用方。只读发现调用方不等于可以改它：报告依赖证据和影响，由用户决定。
