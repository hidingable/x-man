# 给 agent 写文档

skill、agent 定义、conventions、CLAUDE.md 都是写给 agent 读的。目标是让它每次都走同一条路：该做的事一眼看到，做没做完能判断，不该展开的不展开。

下面六条，每条都按「是什么 → 怎么改 → 本仓的改写对照」组织。改完一份文档，逐条过一遍。

## 删掉无效句

模型默认就会做的事，写出来不改变行为，只占注意力。判断方法：删掉这句，行为会不会变？拿不准就跑一次删前删后的对照（项目有 eval 就用 eval，没有就用同一个任务各跑一次），不靠争论。删就删整句，不要只删几个字。

> 改前：执行过程中保持专业、严谨、认真负责的态度。
> 改后：（整句删除）

形容词太弱压不过默认行为时，换一个更强的词，而不是加一段解释。

## 写要做什么

写「不要 X」会让 X 更容易被想到。改成写目标行为，让被禁止的那件事根本不出现。只有写不成正向说法的硬底线才用禁止句，并且配上正向目标。

> 改前：不要复述已有文档内容，不要输出完整调查流水账。
> 改后：已有文档用路径引用；只写结论和支撑它的证据。

## 每一步结束在一个能检查的条件上

「核对完毕」「理解清楚」这种结尾，模型会过早认为自己做完了。完成判据要能区分做完和没做完，最好还写出要做到什么程度。

> 改前：核对代码事实，确认计划与当前代码一致。
> 改后：列出目标数据的全部读取方和写入方（文件:行号），再改第一行代码。

「全部读取方」比「一份改动清单」要求更高，模型会相应地多查。要求高低写在判据里，不用另加一步「要认真查」。

## 一个意思只写一处

同一条规则写在两个地方，改的时候必然漏一处，而且重复会让它显得比实际更重要。规则放在唯一的地方，其他地方用路径引用。

项目里查得到的东西（命令、配置、目录结构、`--help` 输出）也是事实源：文档里只给路径，不抄内容。值得写进文档的是查不到的：没写下来的约定、某个选择的理由、配置不会告诉你的坑。

> 改前：在 skill 里抄一遍 `package.json` 的测试命令列表。
> 改后：根据项目现有命令选择相关测试；命令以 `package.json` 为准。

## 按「每次都用」还是「偶尔用」分层

文档里有两种内容：步骤（按顺序做的事）和参考（需要时查的规则和事实）。按需要的频率分层：

1. 每次执行都要用的步骤和参考，留在主文件。
2. 只有某些情况才用到的，挪进 `references/`，主文件里写清「什么情况下去读哪个文件」。

主文件太长时，步骤会被参考淹没，模型照不照做全看运气。判断标准：每条执行路径都需要的留下，只有部分路径需要的挪走。同一个概念的定义、规则和例外放在同一个标题下，不要散在几处。

> 改前：主文件里同时放着变更审查和模块深度审查两套完整清单。
> 改后：主文件只留选模式的判断，两套清单各放一个 references 文件。

引用写成触发条件加路径，比如「需要比较多个修复方向时，读 `references/xxx.md`」。只写一个路径不写条件，模型不知道什么时候该去读。

## 用模型本来就懂的词

一个模型在训练中见过的词，能用几个字代替一整段描述，而且每次出现都会唤起同样的行为。先找现成的词，找不到再自造；自造的词要在第一次出现时说清楚。

> 改前：反馈要快、结果稳定、开销小，能反复运行。
> 改后：先建一个能稳定复现的最小回路（几秒内跑完，同一输入同一结果）。

同一个意思在三处写成三种说法时，就是该收成一个词的信号。

## skill 带脚本时

脚本是给 agent 跑的。新增或修改 `scripts/` 时，读 `references/agent-tools.md`，按其中六条自检。

## 改完之后

1. 运行项目里针对 skill 的检查。在 x-mansion 仓库里是 `python3 -B -m unittest discover -s tests` 和 `./xman validate`，字数上限和代号写法由 `tests/test_skill_lint.py` 检查，conventions 引用由 `scripts/check-conventions.py` 检查。
2. 改动影响 skill 行为时跑对照，结果对不对不能比改前差。在 x-mansion 仓库里用 `scripts/eval-run.py --cases <相关用例>`。
3. 在 x-mansion 仓库里，字数确实降下来了，就同步调低 `evals/budgets.json` 里的上限。
