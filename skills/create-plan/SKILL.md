# 编码实施计划

计划要让没参与前期讨论的执行者也能可靠实施：文件、调用关系、数据变化、失败处理和验证方式都写清楚，不留给执行者重新猜。授权按 `.ai-configs/conventions.md`〈授权、实现判断与验证〉；工程约束按 `references/engineering-checks.md`。

## 更新模式

已有计划、需求或代码事实变了要调整时，读 `references/update-plan.md`，按它修改现有计划；新增和改写的任务仍按下文〈编写计划〉的要求写。

## 开始前

1. 按 `.ai-configs/conventions.md` 读项目上下文和相关的 analysis、prd、design、plan 产物。
2. 写下一句话成功标准、实施依据、本次范围和明确不改的内容；修 bug 时还有根本原因。
3. 看工作区和当前分支，记下用户已有的改动。
4. 从真实入口追踪调用、规则、权限、写入、读取、异步处理、外部依赖、配置、部署和现有测试；列出全部直接调用方、写入方、读取方和相似实现，修改边界以它们为准。
5. 资料、代码事实或用户目标互相冲突时，先查已有裁决和有效事实源；仍会改变实施结果的，按统一规则确认。名称含义有冲突或含糊时，调用 Skill 工具（参数为 `domain-terms`）。

## 编写计划

### 每个任务是一条完整的薄切片

按可以独立演示或验证的完整行为拆任务，每个任务贯穿这个行为实际涉及的层（数据、接口、界面、测试），名字用实际行为，比如「让过期合同从待续签列表消失」。同一条用户路径不按「先做完后端、再做前端、最后测试」横着切；纯脚本或文档任务也不硬凑层。任务大小以一次连续工作能完成为准，不拆成「打开文件」「新增函数」这种机械动作。

任务要新建模块、改公共接口，或测试从哪个接口进入还没定时，读 `references/module-design.md`，把接口和测试入口写进任务。

每个任务写（字段名同模板）：

- **结果**：完成后什么行为新增或改变了。
- **现状依据**：当前机制、调用关系、需求依据或问题位置。
- **修改位置**：文件、模块、关键符号或新建位置。
- **做法**：数据怎么流动、契约怎么变、失败怎么处理，影响结果的决定写明来源。分清已确认的决定、规范约束和执行者可以自己定的局部细节；后者只写约束和通过标准。
- **同步修改**：调用方、类型、配置、迁移、文档或兼容逻辑；没有就不写。
- **依赖**：前置任务的实际名称。
- **验证**：要新增或修改的测试、执行命令、人工路径和明确的通过标准。
- **回退方式**：涉及数据、公共契约、依赖或部署风险时才写。

### 对照：同一个需求的坏任务和好任务

需求是「合同到期后不再出现在待续签列表」。

```text
❌ 坏任务：修改 RenewalService
   - 修改：services/renewal.go
   - 验证：功能正常

问题：「修改」不是结果，看不出完成后什么行为变了；只列了一个文件，
     执行者不知道另外两个读取方也要改；「功能正常」无法判定。
```

```text
✅ 好任务：让过期合同从待续签列表消失
   结果：到期日早于今天的合同不再出现在顾问端待续签列表和到期提醒里。
   现状依据：状态判断散在三处——services/renewal.go:42 走 service，
            api/handler.go:88 和 report/weekly.go:120 直接读 contract.Status。
   修改位置：services/renewal.go 的 RenewalQuery.pending()
   做法：过滤条件加 expire_at >= today；历史数据里 renewal_status 有 NULL，
        按「未设置视为未过期」处理，不在本任务清洗。
   同步修改：api/handler.go:88、report/weekly.go:120 改为调用 pending()
   依赖：无
   验证：新增 test_expired_excluded；手工路径——建合同 → 改到期日为昨天 →
        刷新列表，通过标准是列表和提醒里都不出现该合同。
```

```text
❌ 该删的任务：优化续签模块的代码结构

问题：不实现目标行为、不更新必要调用方、不防回归、不提供验证证据——
     四条过滤器一条都不满足。想做就单独立项，不搭这次的车。
```

### 顺序和依赖

- 顺序由真实依赖和可验证性决定：通常先权威数据和公共契约，再领域逻辑、调用方和用户反馈，然后迁移与兼容。
- 每个任务自带验证。单个任务证明不了的跨任务检查（如多服务联调）才单列验证任务。
- 现有结构让目标改动只能散着改（同一规则要在多处复制）时，先排一个不改变行为的铺垫重构任务，用现有测试证明行为没变，再做目标行为。只为顺眼的重构仍记进「本次不做」。
- 有并行任务时，列出**当前可开始的任务**及其已满足的依赖；还在等前置交付的，写明在等什么。纯线性的计划不用另列。
- 大范围的机械改动（重命名字段、改公共类型）一次改完会同时打断大量调用方时，按「先加新的形态 → 分批迁移调用方 → 确认没有旧调用后删掉旧形态」排，每批单独一个任务、单独验证。能一次改完并验证的就一次改完，不加过渡层。复杂迁移读 `references/plan-guide.md`。

### 风险和规范

- 按实际改动覆盖：权限、数据归属、并发、幂等、事务和失败恢复；数据结构、配置、接口或依赖变化的兼容与迁移；异步任务、外部服务、部署和回滚；主路径、失败路径、边界和历史行为的回归保护。不相关的风险不写。
- 预计修改路径成型后，调用 Skill 工具（参数为 `spec-query`）。在〈实施依据与边界〉列出命中的 spec id、source 和受它约束的任务，把相关条款写成任务约束和可检查的验证。规范导致修改路径变化时，只对新增路径补查。规范和用户裁决、PRD、契约或代码事实冲突时，按统一规则处理。查询没完成就写「Spec 未完成对账」。

### 交出去之前

逐个任务问一遍：**执行这一步的人，还需要自己决定什么？**

- 已有决定或事实来源的：写清做法、依据和适用边界。
- 局部可逆的实现细节：写清约束和验证方式，交给执行者判断。
- 影响结果的未决决定：先补能自己查到的事实；仍要用户裁决的列成待确认项，现在就问，其他工作继续。

最容易漏的：字段名和返回结构、错误码和状态取值、默认值与超时重试、用户可见文案、边界行为（空、超长、并发冲突）、配置项名字和层级、每个验证具体断言什么。

同时确认：每个任务都直接实现目标、同步必要的调用方、处理已确认的问题或提供回归保护；读写方和调用方覆盖完整；计划不靠编号对照表也能读懂。

写明时间不够时先延后哪个任务、哪些新发现会要求改计划。用户或团队要求估算时才写时间范围及依据。

## 输出

用 `assets/templates/plan-template.md` 写计划文件，按 `.ai-configs/conventions.md` 的 plan 路径保存。对话里只给：

1. 成功标准。
2. 任务顺序和关键依赖。
3. 最大风险或需要用户决定的事项。
