# 工程约束与项目 Spec

> 原为 conventions.md 的同名小节，create-plan、code-by-plan、review、spec-query 等需要核对工程约束时读取。

工程约束分成通用检查方法与项目已采用的规则。先读当前项目的有效规范、接口契约和相关实现，区分已采用规则、现状事实、建议和待定决定。没有登记 Spec 不等于没有约束；AGENTS、现有规范和已确认契约仍是依据。缺少某类规范时，只补当前任务需要的判断，不自动建规范或强制采用 DDD、分层框架、目录名称和组件模式。

按本次影响面检查以下内容；没有该类代码或不受本次影响时跳过：

| 方面 | 必须核对的问题 | 可验证的约束示例 |
|---|---|---|
| 领域 | 规则、不变量、状态变化和权威数据由谁拥有；跨领域通过什么契约协作 | 合同到期判断由约定的业务模块统一提供；边界日期和重复执行有测试，不把判断复制进页面和工具函数 |
| 技术设计 | 模块职责、允许的依赖方向、公共契约、错误与副作用、兼容和替换边界 | 已采用分层的项目按其依赖规则修改；公共签名变化核对全部实际调用方及兼容要求，不凭目录名推断层级 |
| utils | 能力是否通用，是否混入领域身份、规则或业务状态；输入输出、外部依赖和副作用是否清楚 | 通用日期格式化与合同到期政策分别归属；有副作用的工具明确其依赖与失败行为，不因名字含 utils 就认定纯函数 |
| 组件 | 基础组件与业务组件的职责，数据获取和状态归属，公共接口、交互与可访问性 | 已有基础按钮维持约定接口和键盘行为；业务权限判断按项目规则归属，不默认所有组件都禁止取数，也不因出现两处相似代码就强制抽象 |

示例用于核对实际项目的规则归属，不是对所有项目强制指定实现。规则已明确时，计划写清本任务如何遵守；尚未决定且会改变业务或公共契约时列出影响和候选，仅暂停依赖该决定的工作。局部实现细节按〈授权、实现判断与验证〉处理。

项目需要长期规范时，按已有文档结构维护正文，并在 Spec 索引绑定真实适用路径；没有相应目录或模块时不创建空的分类规范。每条规则应说明适用范围、具体要求、原因、例外和验证方式。通用代码质量规则可以被多个路径引用，领域专属规则只绑定相关实现与消费者，不用全仓通配掩盖归属。新增或修改正式规范须在用户授权范围内，未确认建议不能登记成已采用规则。
