# 更新现有编码计划

需求或代码事实变了、要调整现有计划时按本文件做。计划更新要说明为什么变、影响什么、如何继续，不只追加任务。

只有新事实改变成功标准、范围、技术路径、依赖、顺序、风险或验收时才更新计划。普通执行细节和不影响结果的小发现记在进度里即可。

## 开始前

1. 按 `.ai-configs/conventions.md` 定位目标计划、项目上下文和实际执行状态。
2. 先从当前任务和前序产物核对目标计划；仍无法确定或多个目标会改变更新范围时，说明差异并按统一规则确认。
3. 对照成功标准、代码事实和已完成任务，确认变化原因。

## 更新

1. 判断新事实是否改变目标、根本原因、范围、代码位置、调用方、数据与契约、依赖、顺序、迁移、回滚或验收。
2. 已完成任务不改写历史：
   - 结果仍有效：保留完成状态。
   - 部分失效：写清需要重做的实际任务和原因。
   - 完全失效：保留历史记录，新增替代任务，不把旧任务写成未执行。
3. 简要说明原计划哪里失效、准备怎样改、代价和对已完成工作的影响；已有授权覆盖时直接更新，仍有影响结果的未决决定时按统一规则确认。
4. 用实际任务名称增加、删除、重排或拆分任务，并同步依赖和验证方式。新增前置任务时，检查所有调用方和验证任务；删除任务时，清理依赖和验收引用。
5. 新增工作必须写明其中一项：延后或删除哪些任务、交付时间增加多少、为什么仍在原有缓冲内。
6. 删除已经失效的内容，不让新旧计划并存；在文末追加变更记录。

新事实产生的未决事项按统一规则处理；已确认的业务变更直接同步，只暂停依赖未决决定的工作。

状态用中文写事实：已完成、进行中、有风险、阻塞、未开始。

## 变更记录

```text
日期：YYYY-MM-DD
原因：什么新事实使原计划失效
变化：删除、增加或重排了哪些实际任务
影响：已完成工作、交付时间和验证如何变化
```

## 输出

对话只说，直接陈述事实：

1. 原计划为什么不再成立。
2. 任务顺序和范围发生了什么变化。
3. 对已完成工作和交付时间的影响。
4. 当前下一动作。
