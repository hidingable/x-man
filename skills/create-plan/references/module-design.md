# 模块接口与替换点

讨论调用方需要知道什么、复杂度由谁承担、哪里能独立变化时读。写计划、定测试从哪个接口进入、审查结构、扫描架构都用这一份词汇。它是分析工具，不是项目命名规范：沿用领域词、API、service、component、边界等已有清楚含义的名称，有歧义时补一句含义即可；项目已采用的分层和依赖规则优先。

## 术语

| 术语 | 本文含义 | 可以核对什么 |
|---|---|---|
| 模块（module） | 同时有对外使用方式和内部实现的一段能力，大小可以是函数、类、包或跨层业务切片。 | 指出它的调用方、承诺的行为和内部实现，不以目录名推断边界。 |
| 接口（interface） | 调用方为正确使用模块必须知道的全部事实。包括签名，也包括单位、不变量、调用顺序、配置、失败方式和时效要求。 | 写出一个真实调用；数清调用方还必须补哪些校验、初始化和错误处理。TypeScript 的 interface 或 HTTP API 只是其中一种表达。 |
| 实现（implementation） | 模块内部如何兑现行为。 | 调用方是否被迫知道本应藏在内部的数据结构或执行步骤。 |
| 深度（depth） | 接口隐藏复杂度的能力。调用方理解较少的约束，就能可靠完成较多工作时，模块较深。 | 对比调用代码和测试准备工作，而不是拿实现行数除以接口行数。代码短或方法少并不自动代表深。 |
| 替换点（seam） | 能在固定位置替换行为、同时不改动使用该行为的主体的位置。 | 换一个依赖时究竟要改哪里；生产适配器、测试替身或隔离外部系统的需求能否证明它有用。 |
| 适配器（adapter） | 在替换点满足接口的一种具体实现，描述它承担的角色。 | 核对真实系统与替身是否遵守相同错误、时序和副作用契约；文件里有多少代码不决定其角色。 |
| 局部性（locality） | 一条规则的知识、修改和验证能否集中在相邻位置。 | 用一次实际规则变更列出必须修改的文件、需要理解的跳转和要跑的测试。少建文件不等于提高局部性。 |
| 接口收益（leverage） | 调用方学会这份接口后获得的能力，以及同一改动能让多少真实调用点共同受益。 | 比较能移除多少重复决策、校验或测试搭建；复用点数量必须来自当前调用链，不能假设未来用户。 |

## deletion test：设想拿掉这一层

这是只读的反事实检查，不实际删除代码。

1. 列出该模块当前承担的职责，以及真实调用方依赖的约束。
2. 设想调用方直接访问下一层。哪些校验、错误归一、顺序控制、权限或兼容处理会重新出现在各个调用方？
3. 若主要减少了透传和跳转，且上述职责确实不存在，这一层有收缩空间；若复杂度只是扩散到调用方，它正在承担有用工作。
4. 用代表性调用草图和相应验证说明判断。缺少调用方或历史证据时，保留为待验证假设。

例如，支付门面只有十行，也可能集中幂等键和错误翻译；删除它会把同一规则复制到每个支付入口。相反，一个只重新命名参数、没有独立约束的转发层，可能让每次排障多跳一次。两者需要逐项核对职责，不能只看代码长度。

## 用词不能替代设计证据

- 小接口可以隐藏复杂内部结构，但不能把错误和副作用藏到调用方无法判断的程度。
- 对外行为适合从公开接口验证；内部测试是否保留，要看它是否定位重要算法或约束，不强行删除。
- 第二种适配器是存在变化需求的证据之一，不是建立替换点的最低数量要求。外部系统隔离、确定性测试或已确认迁移也可能提供理由。
- 集中一条规则可能提高局部性，但把无关规则堆进一个大模块会增加耦合；需要说明具体收益与代价。
- 把 service 改叫 module、把 API 改叫 interface，不会自动改善设计。名称已清楚时保留，必要时解释讨论的是哪一部分契约。

## 写进计划时

- 新建或修改模块的任务，写出对外接口（签名、失败方式、调用约束）和测试从哪个接口进入；优先沿用已有接口，需要新替换点时放在能覆盖目标行为的最高一层，数量越少越好。
- 只有绕过接口才测得到时，先检查接口形状，再决定是否加内部测试。
- 依赖按类型决定测试怎么跨过替换点：纯计算直接测；有本地替身的（内存数据库、临时目录）在测试里跑替身；自己的远程服务在替换点定接口，测试用内存适配器；第三方服务注入后用 mock。
- 接口形状本身有争议、几种设计会改变调用方或公共契约时，列出候选接口，各写调用方要知道什么、测试从哪进入，按〈授权、实现判断与验证〉的边界问题处理。
