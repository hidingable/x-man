# 脑暴与方向探索

先打开解法空间，再帮助用户收敛。先验证问题本身，是为了避免围绕错误的前提发散。

## 开始前

1. 按 `.ai-configs/conventions.md` 读取项目上下文。
2. 搜索相关的脑暴、分析、需求和设计产物，复用已经验证的结论。
3. 把已知事实、用户判断和未验证假设分开。资料不足不等于必须追问；先完成安全的只读调查。

## 判断当前重点

- **验证问题**：问题是否成立、谁受影响、现有替代方式和实际代价都不清楚。
- **探索方向**：问题基本成立，需要打开产品、流程、规则、数据、组织或技术等不同解法空间。
- **比较取舍**：已经有多个候选方向，需要补足假设、代价和验证方法后再选择。

当前重点不明确且会改变讨论方式时，先向用户确认；上下文已经明确时直接开始。

## 执行

1. **理解问题**：说清谁在什么场景受阻、当前怎样应对、不处理的代价，以及用户提出的是问题还是已经预设的解法。
2. **补足场景**：覆盖主要场景、失败场景、边界场景和可能改变方向的约束，不急着讨论实现细节。
3. **挑战前提**：检查问题是否真实、原因是否只是猜测、现有能力是否已经能解决，以及“不做”会发生什么。
4. **发散**：给出 2~3 个机制真正不同的方向，解法空间确实大时再多给。可以从产品能力、业务流程、规则与权限、数据与自动化、组织协作和技术实现中选相关角度；同一页面的布局调整或同一方案的措辞变体算同一个方向。
5. **反向思考**：其中一个方向是最小改动或不新增能力的做法；合理时考虑删除、合并、自动化或改变流程。
6. **比较取舍**：说明每个方向解决什么、收益、代价、关键前提、主要风险和最低成本的验证方式。
7. **协助收敛**：信息足够后给出推荐、为什么暂不选其他方向、什么证据会改变推荐，以及下一步验证动作。

实际只有一两个合理方向时，说明解法空间为什么有限，不凑数。

## 与用户交流

需要和用户多轮确认的事，按 skill 安装目录里的 `req-analyze/references/grilling.md` 的追问方法进行：每轮把前提已定的问题一次问完并附建议答案，事实自己查。本 skill 另外要求：

- 发散前的事实（谁在用、多久遇到一次、现在怎么绕开、有没有硬期限、什么算解决了）互不依赖，一轮问完。
- 每次得到回答，先复述更新后的理解，再继续追问或发散。
- 用户先抛出方案时，先承认它，再问「还有什么能解决同一个问题」，然后才细化。
- 用户说「差不多了」时，检查方向是否真正不同、关键前提是否明确，再决定收敛。
- 用户的方案站不住时，直接说出来并给依据。前几个方案通常是任何人都能想到的。

## 输出

讨论过程按需要逐步展开，不要求每轮都输出完整文档。收敛后的记录包含：

1. **问题与目标**：真实场景、当前困难、实际代价和已确认约束。
2. **关键前提**：已经验证什么，哪些假设仍会改变方向。
3. **探索方向**：按实际含义命名，保留真正不同的候选方案及其取舍。
4. **推荐方向**：当前建议、理由、暂不选择其他方向的原因。
5. **验证动作**：最低成本的实验、观察或用户确认。

需要留档时，使用 `assets/templates/brainstorm-template.md`，按 `.ai-configs/conventions.md` 的 brainstorm 路径保存。轻量讨论直接在对话中完成。

## 表达规则

命名、提问和输出的通用规则见 `.ai-configs/conventions.md`〈表达与命名〉，核心一条：方案、前提、风险和结论用实际含义命名，不用 `方案 A` 这类代号。本 skill 另外要求：

- 收敛后先写推荐，再写依据；发散过程中的方向保留到收敛为止。
- 方案名要能看出机制差异，不能只是同一方向的措辞变体。

## 质量检查

- 推荐方向是否对应已确认的问题和原因。
- 方向之间是否机制不同，而不是同一方向的页面、参数或实现微调。
- 是否包含最小改动或不新增能力的方向。
- 是否说明为什么不选其余方向，以及什么证据会改变推荐。
- 是否删掉重复背景和空章节，同时保留理解取舍所需的场景、前提和风险。

需要更多发散方法时，读 `references/brainstorm-guide.md`。
