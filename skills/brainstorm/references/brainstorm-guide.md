# 脑暴方法补充

仅在问题复杂、证据冲突或方案差异难以说清时读取。

## 先判断问题是否成立

优先找三类证据：

- **行为证据**：用户实际做了什么、绕了什么路、花了多少时间。
- **结果证据**：失败率、流失、成本、投诉或交付延误。
- **约束证据**：合规、预算、权限、组织和技术边界。

用户提出的按钮、页面或技术选型属于方案，不属于问题证据。

## 追到可改变的原因

用下面的链条检查：

```text
可观察现象 → 直接机制 → 形成机制的约束 → 可以改变的最浅原因
```

每一跳都要有证据。缺证据就写“尚未验证”和最小验证动作。

## 打开解法空间

默认给出 2~3 个机制真正不同的方向，解法空间确实大时再多给。优先从不同机制出发，而不是改变同一页面的布局或同一接口的参数：

- 调整产品能力或用户入口。
- 改变业务流程、职责或协作方式。
- 修改规则、权限、状态或提醒机制。
- 利用数据、自动化或智能处理减少人工步骤。
- 调整技术实现、系统边界或外部集成。
- 不新增能力、删除现有步骤或用最小改动验证问题。

不要求每类都出现，只选择与真实问题有关的角度。实际只有少数合理方向时，说明限制来自哪些事实或约束，不制造同义方案。

每个方向写清：解决机制、适用场景、收益、代价、关键前提、主要风险和最低成本验证方法。

## 形成推荐

推荐必须回答：

- 为什么它最直接处理根本原因。
- 为什么当前不选其他方向。
- 最小切口是什么。
- 什么新证据会改变推荐。

## 提问

先自行查证，再问会改变方向的问题。**发散前的事实收集一次问完**（谁在用、多久遇到一次、现在怎么绕开、有没有硬期限），只有互相依赖的选择才一个一个来。选项使用完整语义，例如问“优先验证用户是否愿意使用，还是优先验证技术可行性”，不要让用户回复 `1A` 或 `2B`。用户回答后，先说明当前理解怎样变化，再继续。

## 写作

先给结论，再给依据。标题用实际含义，不使用方案字母、需求编号或风险代号。轻量脑暴直接在对话中完成；需要留档时使用模板，并删除所有空章节。
