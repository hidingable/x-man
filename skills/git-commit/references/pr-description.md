# PR / MR 描述

用户要写 PR 或 MR 描述时读。描述只回答审查者合并前要知道的三件事：改了什么、怎么证明能用、合并后出问题有多难收回。不写开场白，名称按项目上下文的术语表。

## 模板

```markdown
## 改了什么

<最小示意 + 一两句说明>

## 证据

- 改前：<失败的测试、报错输出或截图>
- 改后：<同一条命令或同一路径的通过结果>

## 合并风险

能否撤回：<能直接回滚 / 撤回有代价，写清代价>
影响范围：<一个词，再写可能受影响的调用方、页面或数据>
```

## 改了什么

选一种最小的示意说清要点，示意旁边紧跟它说明的那句话。只留回答这次审查问题需要的调用、文件、状态和边界：

- 逻辑或算法改了：伪代码。
- 运行时调用顺序改了：调用树，必要时用 `diff` 标出新增和删除的调用。
- 文件职责或大范围重构：浅层文件树，每个目录后注一句职责。
- 组件结构改了：组件树，标出状态和模块边界。
- 多方交互或数据流：Mermaid 时序图。
- 大部分是新代码，或省略上下文会看不出归属和顺序：贴完整代码块。

```diff
 on(save)
-  write content
+  if content is unchanged
+    return cached result
+  write new content
+  invalidate cache
```

一般一到两种就够，不把每种都用上。

## 证据

给改前和改后的对照，两边用同一条命令或同一条用户路径。本 skill 只用 Git，不自己跑测试，证据从已有记录里取：当前任务的 review、harness、verification 产物，本次会话里已经跑过的命令输出，或用户提供的截图和日志。界面改动有截图时用截图；其次是测试或命令输出，写出那条由失败变成通过的测试。引用时说明覆盖范围；只有「测试通过」一句话不算证据。贴输出前先把密钥、token、连接串、内网地址和真实用户标识换成 `<REDACTED>`。

找不到证据的项写「未验证」和原因，不为了填这一节去跑命令。

## 合并风险

- **能否撤回**：回滚一次提交就能完全恢复的，是能直接撤回；涉及数据迁移、删数据、对外发布的接口或消息格式、第三方回调等改动，回滚代码也恢复不了，写清撤回要付出什么。
- **影响范围**：把可能受影响的面都过一遍：下游调用方、共享组件、页面布局、移动端、权限、数据和定时任务。写实际会波及的，不确定的标「待验证」。
