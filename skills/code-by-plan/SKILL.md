# 按计划实施

按已确认的目标和步骤实施，每个任务都用本次验证证明结果。授权、局部细节和「本次不做」按 `.ai-configs/conventions.md`〈授权、实现判断与验证〉；已有证据能不能直接用按〈阶段职责与证据复用〉。

## 开始前

1. 读项目上下文和当前计划；用户在对话里给了完整步骤也可以直接用。做到能说出成功标准、范围和验证方式，修 bug 时还要能说出根本原因。
2. 看工作区：记下已有的、与本任务无关的改动，后面不碰它们。
3. 核对规范：计划已经对过 Spec 的直接用；单独调用、计划没对账，或实际要改的路径超出计划时，调用 Skill 工具（参数为 `spec-query`），只补查新增部分。查询失败记为「Spec 未完成对账」。涉及领域规则、模块依赖、utils 或组件边界时，按 skill 安装目录里的 `create-plan/references/engineering-checks.md` 核对。
4. 跨会话或多任务时用 `assets/templates/progress-template.md` 记进度；短任务不建进度文件。
5. 简短说明成功标准和第一个任务，然后开始。

## 每个任务一个循环

1. **重读任务**：目标、修改位置、依赖、通过标准。
2. **核对代码事实**：列出目标数据或行为的全部读取方和写入方（文件:行号），连同数据契约、配置和现有测试，然后才改第一行代码。计划写的是当时的理解，代码是现在的事实。
3. **记录现状**：行为变化先记下当前基线；修 bug 先跑一遍复现。建不起来就写明原因。
4. **最小完整修改**：改目标机制，同步必要的调用方、类型、配置、迁移、错误路径和用户反馈。
5. **验证**：先跑最接近本次行为的检查，再按影响扩到相关模块和真实用户路径。
6. **看差异**：计划内的都改了，没混进无关改动，用户原有的修改都还在。
7. **记进度**：结果、验证、下一个任务。会再踩一次的坑（环境依赖、工具行为、代码里的隐性约定、试过走不通的做法）单独记一条：现象、原因、下次怎么绕开。

一次只做一个任务。「核对代码事实」做出来是这样：

```text
任务：统一合同状态读取来源

计划说：改 RenewalService.getStatus()
实际查：
  grep -rn "getStatus\|renewal_status" --include=*.go
    → 3 个读取方：api/handler.go:88、jobs/expire_notify.go:31、
      report/weekly.go:120（计划只提到第一个）
  读 handler.go:88 → 直接读了 contract.Status 字段，没走 service
  读 migrations/ 最新一版 → renewal_status 有 NULL 记录（老数据）
结论：计划的修改点不足以统一来源，jobs 和 report 两处必须一起改；
     NULL 分支需要在这次处理，否则统一后报表会少数据 → 按偏离规则记录后继续。
```

换技术栈只是换命令：TypeScript 项目用 `rg "getStatus" --type ts` 加 `tsc --noEmit` 看调用点是否跟上；Python 项目查完调用方，还要确认有没有靠 `getattr` 的动态访问。

## 计划没写或对不上时

| 遇到的情况 | 怎么做 |
|---|---|
| 计划没写某个实现细节 | 先查代码、契约、已确认设计和规范，有现成做法就沿用；没有就按局部细节规则自己定，记下理由。用户可见文案、页面跳转、公共字段、状态取值、默认业务行为、超时重试对用户的影响，要有明确依据，按边界问题处理。名称含义有冲突或含糊时，调用 Skill 工具（参数为 `domain-terms`） |
| 想改计划外的东西 | 重构、新功能、顺手修 bug、改命名，都记进「本次不做」。完成当前目标必需的调用方和配套属于范围内，写明它和目标的关系 |
| 计划和代码事实对不上 | 以代码事实为准。完成目标必需的偏离（比如计划漏掉的读取方）记下原因后继续。要引入新依赖、改公共契约、扩大用户可见范围，或计划的做法只能遮住症状、任务顺序或验收方式不成立时，按边界问题处理：只暂停受影响的任务，在计划文件里写明发现和建议的调整，按 `.ai-configs/conventions.md`〈向用户提问〉问用户，定下来后再改 |
| 出错 | 先停下，不再扩大修改，记下现象、根本原因（没确认就写「尚未确认」）、对成功标准的影响和决定。用日志、测试、差异比较或只改一个变量的实验找原因；连续修改无效时回到最初的假设重新检查 |

测试预期来自需求、契约、原始复现或其他独立事实，不按新实现反推。

## 子代理或无人值守时

需要用户裁决的事，记下已查事实、缺口、各选项的影响和建议，只暂停依赖它的任务，其他任务继续。剩下的任务全都依赖它时，回报阻塞。

## 完成前

逐条确认，每条都要有本次的证据：

- 每条成功标准都满足；修 bug 时，根本原因、失败路径和回归都验证过。
- 必要的调用方、读写方、配置、迁移和文档都已同步。
- 只改了本任务相关的文件，用户已有的内容都还在。
- 进度文件和实际状态一致。
- 没跑成的验证写了原因和风险。

## 输出

工作中只说当前任务、关键结果、阻塞和下一步。完成时写：

1. **修改结果**：哪些文件的什么行为变了。
2. **依据**：一句话说目标机制和修改边界；修 bug 时写根本原因。
3. **验证**：实际执行的命令或操作及结果。
4. **未验证或未完成**：只在确实有时写；没有就整项删掉，不写「无」。

跨模块、有迁移或执行中发生偏离时，读 `references/code-guide.md`。
