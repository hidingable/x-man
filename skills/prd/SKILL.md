# 产品需求文档

把已经确认的产品决策写成完整、无歧义、可验收的行为约定。对话摘要可以短，PRD 本身要把角色、规则、状态和失败路径写全。授权按 `.ai-configs/conventions.md`〈授权、实现判断与验证〉；工程约束按 skill 安装目录里的 `create-plan/references/engineering-checks.md`。

## 整理模式

前面的对话或已有产物已经把问题、范围和关键决定讨论清楚时，不再重新提问，直接把它们整理成 PRD：用对话里定下的叫法，引用已有分析，只把对话里确实没覆盖、又会改变产品行为的缺口列进「风险与未决问题」。

## 更新模式

已有 PRD、需求变了要同步时，读 `references/update-prd.md`，按它修改现有文档；改动到的内容仍按下文〈内容〉的要求写。

## 开始前

1. 按 `.ai-configs/conventions.md` 读取项目上下文和相关 analysis、prd 产物。
2. 核对当前有效的需求来源和版本。用户原话、分析、旧 PRD、原型与现有实现冲突时，先核对已有裁决和事实源；仍会改变产品决策的冲突说明影响并确认，不自行选择有利版本。
3. 有可信分析时引用结论和证据，不整段复制。
4. 没有可信分析时，依据当前输入和相关事实补齐必要调查，再生成文档；已有信息足够时直接继续，不增加是否先分析的形式确认。
5. 直接生成时，从用户输入和现有实现中确认用户问题、目标、范围和完成标准；问题形成原因只有在影响产品决策时才展开。
6. 关键产品决定写明来源：用户已确认决定、有效契约或规范、现状事实、分析建议。现状说明当前行为，不能自动成为期望规则；建议和基于假设的内容保留相应状态。文档存在、保存或格式完整不代表全部决定已获用户认可。

## 内容

### 先给结论

用一小段说明：要解决什么问题、选择什么方向、预期产生什么结果。

### 用户问题与目标

- 具体角色、入口和场景。
- 现有流程为什么不能满足，以及哪些原因会影响产品决策。
- 目标写可观察结果，不写“新增某页面/按钮”之类实现输出。

### 范围和优先顺序

按语义分组：

- **本次必须交付**：缺少它就无法解决核心问题。
- **本次应该交付**：缺少它仍可交付，但价值或可用性明显下降。
- **可以延后**：不影响本次结果，可后续处理。
- **明确不做**：容易被误解为范围内的内容及原因。

分组名就用上面这几个，需求用实际名称。新增范围要说明移除什么或延长多少时间。

### 用户行为、规则和状态

角色、业务对象或状态含义影响规则与验收时，调用 Skill 工具（参数为 `domain-terms`）核对含义，将确认的含义和适用边界写进相关行为与验收。

按实际功能名称写清：

- 谁从哪里进入，能看到什么，能执行什么。
- 操作前置条件、权限和失败反馈。
- 数据保存在哪里，刷新、重试或重新进入后怎样表现。
- 状态如何变化，当前状态对应什么下一步。
- 谁会收到提醒，何时提醒，如何追溯和归档。

复杂流程还要写清：

- 每个状态由什么事件进入，谁拥有下一动作，允许和禁止哪些操作。
- 重复提交、并发处理、超时、撤回、重试和部分成功怎样处理。
- 权威数据来自哪里，谁可以修改，修改后哪些角色能看到。
- 与外部系统、异步任务或人工环节衔接失败时，用户如何知道并恢复。

技术约束只写影响产品行为的；文件路径和代码片段很快会过时，留给实施计划。原型里的状态机、数据结构等比文字更精确的决定，可以摘录关键部分并注明来自原型。

### 质量与运行约束

只在实际需要时写性能、容量、可用性、安全、隐私、审计、兼容性和数据迁移要求。每项都写适用场景和验证方式，比如「列表 1 万条数据时首屏 2 秒内出现」。

### 验收标准

每条写成“角色 + 前置条件 + 动作 + 可观察结果”。至少覆盖主路径、权限失败、业务失败、重复操作、刷新恢复、状态衔接和最终完成结果；只保留与本需求有关的场景。

「快、易用、稳定、正确」这类词后面紧跟可验证的标准；无法量化时写明由谁、在什么场景人工确认。

### 风险与未决问题

只写会改变范围、行为、交付时间或合规性的内容。每项说明影响、触发条件和处理方式；未决问题说明需要什么证据。

## 核对未决问题

- 仍会改变角色、范围、规则、状态、验收或兼容性的问题，按 `.ai-configs/conventions.md`〈表达与命名〉的提问规则确认，说明不同理解造成的实际差异。
- 用户要求基于某个假设继续时，在 PRD 里写出假设及风险，保持「假设」的状态。
- 写完后概括目标、范围、关键规则和仍未解决的问题，按已有授权保存。

## 输出

使用 `assets/templates/prd-template.md`，按 `.ai-configs/conventions.md` 的 prd 路径保存。简单需求允许删减无关章节；复杂需求按实际需要展开，不能用固定篇幅限制产品规则。

### 前端改动 demo

PRD 改变现有页面的展示或操作时，落档后按 `references/frontend-demo.md` 照抄现有页面样式，生成带简单交互的 HTML demo 和说明。

### 表达规则

通用规则见 `.ai-configs/conventions.md`〈表达与命名〉。本 skill 另外要求：

- 结论放在最前，背景只保留理解结论所需的信息。
- 删除模板说明和不影响交付的实现细节；产品规则写全。

## 完成检查

- 每项范围是否都能追溯到真实问题、目标或已经确认的产品决策。
- 角色、入口、按钮、状态、下一步、提醒、追溯和完成结果是否闭合。
- 权限、失败、重复操作、刷新恢复、异步或人工衔接是否在相关场景中写清。
- 每个用户可见行为是否有明确失败反馈和验收方式。
- 非目标是否阻止常见范围误解。
- 读者是否无需查编号对照表就能理解每条结论。
- **下游还需要自己决定哪些产品行为**：状态取值、边界行为、失败文案、谁有权限。有来源的写清依据，影响结果的未决事项按统一规则确认，让实施者不用猜产品决策。
- 涉及页面改动时，demo 和说明是否已生成并通过自检。

需要更多写作说明时，读 `references/prd-guide.md`。
