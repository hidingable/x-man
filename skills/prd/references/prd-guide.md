# 产品需求写作补充

仅在角色、状态、规则或验收关系复杂时读取。

## 需求必须形成完整业务流程

对每项功能检查：

1. **入口**：谁从哪里开始。
2. **依赖**：需要什么权限、数据或前置状态。
3. **动作**：用户和系统分别做什么。
4. **保存**：结果写到哪里，刷新后是否仍存在。
5. **状态**：成功、失败、等待和重试如何表现。
6. **下一步**：当前状态下谁继续处理。
7. **完成**：怎样追溯、提醒和归档。

缺少任一关键环节，就不是完整业务能力。

## 范围优先顺序

- **本次必须交付**：缺少就不能解决核心问题。
- **本次应该交付**：缺少仍能交付，但价值或可用性明显下降。
- **可以延后**：不影响当前结果。
- **明确不做**：容易被误解为本次范围的内容。

不要用 `P0/P1/P2` 代替含义。新增范围必须同步减少其他范围或延长时间。

## 功能规则

每条规则使用实际名称，并写：

```text
触发条件 → 系统行为 → 用户可见结果 → 失败反馈 → 下一步
```

不要用需求编号作为标题，也不要写“详见需求三”这类回查引用。

## 状态变化

状态多时，用状态实际名称组织：

- 如何进入。
- 谁能看到和操作。
- 允许的下一动作。
- 成功后进入什么状态。
- 失败、超时和撤回如何处理。

## 验收标准

优先覆盖主路径、权限失败、业务失败、数据异常、重复操作、并发或超时、刷新恢复、跨角色衔接和最终归档。只选择真实存在的场景，不为模板完整编造能力。每条标准必须能由测试或明确人工步骤验证。

## 多来源冲突

当用户原话、分析报告、旧 PRD、原型、接口契约和现有实现不一致时：

1. 列出冲突的完整语义，不用文档编号代替内容。
2. 判断冲突会改变哪些角色、规则、状态或验收标准。
3. 能从更新日期和明确声明确定当前基线时使用最新有效基线。
4. 仍无法确定时停下来向用户确认，不把旧行为偷偷写回新 PRD。

## 技术内容边界

PRD 只保留会改变用户行为、范围、合规或验收的技术约束。模块划分、类名、组件树和详细接口实现不写进 PRD。

## 写作

结论第一，背景最少。引用已有资料时写路径或语义标题，不复制全文。删除空章节和模板说明。整篇文档不使用字母编号、组合编号或仅靠编号才能理解的交叉引用。
