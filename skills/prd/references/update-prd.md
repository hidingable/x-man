# 更新现有 PRD

需求变了、要把变化同步进现有 PRD 时按本文件做。根据新事实修改现有文档，并修复变更造成的连锁不一致；只在末尾追加一段文字不算完成。

## 开始前

1. 按 `.ai-configs/conventions.md` 定位目标 PRD 和项目上下文。
2. 先从当前任务和前序产物核对目标 PRD；仍无法确定或多个目标会改变更新范围时，说明差异并按统一规则确认。
3. 写清旧结论、新事实、变化原因和实际生效范围。

## 更新

1. 找出直接变化的目标、范围、角色、入口、用户行为、规则、权限、状态或验收标准。
2. 沿业务关系和文档引用检查受影响的前置条件、失败反馈、下一步、提醒、追溯、归档和质量约束：
   - 目标改变：重新检查问题、范围和全部验收标准。
   - 范围改变：同步非目标、角色权限、状态和里程碑。
   - 规则改变：同步入口、交互、失败反馈、数据和测试。
   - 新证据推翻旧结论：明确删除旧结论，不并排保留冲突说法。
3. 简要说明变化内容、连锁影响和版本处理方式；已有授权覆盖时直接更新，仍有影响产品行为的未决决定时按统一规则确认。
4. 局部修正直接更新原文件。方向、目标或核心流程发生变化时保留旧版并生成新版本，新版写清替代关系和生效日期。
5. 删除或改写已经失效的内容，并搜索旧术语、旧状态和旧验收表述，确认没有残留冲突。每个新增行为都要有失败反馈和验收方式，每个删除行为都要清理引用。
6. 在文末追加变更记录。

只修改必要内容，不顺手重写无关章节。新内容用实际功能和规则名称，不引入需求代号。

新事实的生效范围、版本归属或业务含义仍不确定且会改变文档结论时，按统一规则确认；已确认的业务变更直接同步，其他独立工作继续。

## 变更记录

```text
日期：YYYY-MM-DD
原因：什么新事实触发变化
变化：旧行为 → 新行为
影响：哪些范围、规则、验收或实施资料需要同步
```

只写影响决策和追溯的信息，用实际内容记录，不用变更编号或章节编号代替。

## 输出

对话只说，先说变化后的结论和原因：

1. 哪个业务结论发生了变化。
2. 改了哪些语义内容。
3. 哪些实施或验收内容因此需要同步；编码计划受影响时，提示用 `/create-plan` 更新计划。
4. 仍未解决的问题。
