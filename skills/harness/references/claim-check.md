# 只核对完成声明

适用条件见 harness 的〈选择验证范围〉。先写清要核对的具体声明。

没有覆盖当前对象的有效证据，不得声称完成。

只核对「完成」这个声明有没有证据支持：已有检查记录覆盖时直接引用，只补缺口。整轮交付验收按 harness 正文，找缺陷是 review 的事。证据能不能复用按 `.ai-configs/conventions.md`〈阶段职责与证据复用〉。

## 执行

1. **确定完成标准**：列出用户要求和本次改动必须证明的结果。
   无法从用户原话、现有规格或代码事实确定，且不同理解会改变完成结论时，停下来按〈表达与命名〉的提问规则确认。
2. **补足证据**：按公共复用规则核对已有结果，只对缺口或失效部分运行项目命令和真实用户路径；不能运行的部分明确说明。
3. **阅读结果**：确认失败、警告、跳过项和执行范围，不只看退出码。
4. **逐条对照**：每个完成标准附对应命令、关键输出、代码位置或人工操作。
5. **如实声明**：证据全部支持才说完成；否则说未完成或未验证，并指出下一动作。

## 最低证据

- **代码逻辑**：相关测试，加上项目要求的类型、lint 或构建检查。
- **Bug 修复**：原复现步骤在修复后得到预期结果，并覆盖必要回归。
- **配置或依赖**：解析或构建成功，受影响功能可运行。
- **文档**：格式、链接、引用和相关校验通过。
- **用户流程**：入口、权限、状态、失败反馈、保存和完成结果都能观察。
  界面类改动**去看一眼**，别用「界面应该会显示」代替。Web 项目使用宿主浏览器能力、
  项目已有的浏览器测试工具或 `web-access` 的 CDP Proxy 跑真实路径，观察入口、操作、
  页面实际内容和截图，把结果作为证据交出来。遵守用户指定的工具；跑不了就说跑不了。

  截图之前先等页面稳，报错和失败请求也要一起看，否则截到的可能是半张图、
  或者页面上红着一片你却没发现。使用所选工具的页面稳定等待、控制台和失败请求检查能力。
  工具无法观测其中某项时明确列为未覆盖，不把缺少观测写成没有错误。

  选择 CDP Proxy 时，可用 `web-access` 的 `scripts/xman-verify.mjs`。
  先加载实际安装的 `web-access/SKILL.md`，按其〈脚本资源路径〉将 `WEB_ACCESS_DIR`
  设置为该 skill 所在目录的绝对路径，并确认脚本存在；不按业务项目根目录拼接母仓路径。

  ```bash
  P="${WEB_ACCESS_DIR:?先设置实际加载的 web-access 目录}/scripts"
  node "$P/xman-verify.mjs" doctor                  # 看 proxy 通不通、有哪些标签页
  node "$P/xman-verify.mjs" arm --target <ID>       # 先装记录器，再操作页面
  # …这中间用 cdp-proxy 的 /click /eval 走完真实路径…
  node "$P/xman-verify.mjs" wait-settle --target <ID> # 等稳了再截图
  node "$P/xman-verify.mjs" console --target <ID>     # 有 error 就退出码 2
  node "$P/xman-verify.mjs" network --target <ID> --only-failed
  ```

  不确定入口和路径怎么走，先查 Feature Map（`xman features list`，内容在 `.ai-configs/features/`），
  别每次重新摸一遍应用。地图和实际对不上时以实际为准，并当场把地图改掉。

  CDP 探针的三条检查命令任意一条退出码为 2，就是发现了问题，不是「跑完了」。
  `wait-settle` 超时同样是证据：说明页面还在动或有请求挂着，如实写进「未覆盖」。
  页面跳转后记录器会丢，跳完要重新 `arm`。

验证范围按风险决定，不必每次跑全量测试。无法执行的验证写「未验证」和原因。

结果不稳定的检查按 `.ai-configs/conventions.md`〈阶段职责与证据复用〉的样本与声明判据处理。

## 输出

只写：

1. **结论**：已验证完成 / 尚未完成 / 部分未验证。
2. **证据**：新运行或复用的命令、操作及关键结果，引用已有记录并说明覆盖范围。
3. **未覆盖**：原因、风险和一个下一动作；没有则删除。

默认只在对话里输出；需要留档时按 `.ai-configs/conventions.md` 的 verification 路径保存。

两个样例，说明「有证据」和「没证据」分别长什么样：

```text
结论：部分未验证。
证据：
- pytest tests/payroll -q → 42 passed, 1 skipped（skip 的是 test_export_pdf，
  缺 wkhtmltopdf，本次改动不涉及）
- ruff check payroll/ → All checks passed
- 手工：顾问端导入 3 行工资表 → 期间外那行提示「不在核算期间」且不阻断提交
未覆盖：老板端同一张表没跑过，因为本地没有老板端账号。风险是两端提示文案可能
       不一致。下一动作：用测试账号跑一遍老板端导入。
```

```text
❌ 不接受的写法：
结论：已完成。
证据：改动很小，逻辑和原来一致，应该没问题；之前跑过测试是通过的。
```

后者的问题不是语气，是「之前跑过」不是本次改动后的证据，「应该没问题」没有对应任何一条完成标准。

### 表达规则

通用规则见 `.ai-configs/conventions.md`〈表达与命名〉，核心一条：用完成标准的实际名称，不写「标准 1」这类编号。这里另外要求：

- 不粘贴完整长日志；保留命令、通过数、失败数和关键错误。
- 不用“应该、大概率、看起来、之前跑过”作为证据。
- 不重复实施总结，验证结论只回答“什么被证明了”。
