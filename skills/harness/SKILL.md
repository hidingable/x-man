# 实施结果验证

回答一个问题：当前对象能不能交付——目标满足了没有、有没有引入回归。只验证和报告，不修代码、不改计划。计划、进度和执行者的完成声明都不算证据，自己核对真实结果。

已有判断和证据覆盖当前目标与回归时直接复用，按 `.ai-configs/conventions.md`〈阶段职责与证据复用〉核对适用范围。实现有没有超出计划、有没有缺陷，由 review 的「需求」和「缺陷与规范」两条线负责；本 skill 只引用它们的结论，不重做。

## 选择验证范围

- **交付验收**：用户要求验收、上线前检查或确认整体能否交付时，继续下文，核对目标和回归。即使用户说实现已完成，仍以实际结果作判断。
- **只核对完成声明**：用户明确只要核对某条完成声明，或当前阶段收口只需核对准备作出的声明时，读 `references/claim-check.md`，逐条核对声明和证据，只补缺口。

## 开始前

1. 读用户目标、成功标准和相关需求或计划；没有正式文档时，从用户原话整理出最低完成标准。
2. 记下验证对象：基准提交、实际文件范围和变更指纹（Git 项目的指纹要包含范围内的未跟踪文件）；非 Git 项目写可复核的版本和文件范围。
3. 按改动范围定验证强度：单步任务做核心检查，跨模块或高风险改动覆盖完整关键路径。
4. 成功标准、目标版本或验证范围有不同理解、并且会改变结论时，先自己查证；还不明确就按〈表达与命名〉的提问规则问。

## 验证

**目标是否满足**：逐条检查用户可见行为和完成标准，每条附代码位置、测试结果或可复现的操作。标准缺失或无法测试时直接指出。

**是否引入回归**：
- 复用适用的已有结果，只补跑受影响或没覆盖的测试、lint、typecheck、build 或运行时检查。命令从项目自己的配置里读。
- 沿实际改动搜索公共契约、数据结构和状态的读取方和写入方，覆盖涉及的客户端、服务端、数据层、任务、脚本和交付配置。
- 覆盖主路径、失败路径、权限、边界和恢复行为。

没有运行证据的部分，不签运行期通过；跑不了就写原因。结果不稳定的检查按〈阶段职责与证据复用〉写清条件和次数。

## 输出

1. **验证对象**：基准提交、文件范围和变更指纹。
2. **结论**：可以交付 / 修复后交付 / 需要重做，加一句原因。
3. **未满足的结果**：实际名称、证据和影响。
4. **回归检查**：新运行和复用的结果，及覆盖范围。
5. **未验证事项**：有才写，附原因、风险和下一步。

需要留档时按 `.ai-configs/conventions.md` 的 harness 路径保存。样例（Go 服务）：

```text
验证对象：基准提交 a1b3f9c，改动 3 个文件——services/renewal/state.go、
          api/handler.go、migrations/0007_renewal_status.sql（未跟踪，已计入指纹）
          变更指纹 sha256 f4c1a0…
结论：修复后交付——续签状态能正确落库，但过期分支没有回归保护。
未满足的结果：
- 「合同过期后不再进入待续签列表」无测试覆盖。handler.go:88 只在 status 为
  active 时过滤，expired 走同一分支，实测过期合同刷新后仍显示「待续签」。
回归检查：
- go test ./services/renewal/... → 14 passed
- go vet ./... → 无输出
- 手工：新建合同 → 改到期日为昨天 → 刷新列表（复现上面那条）
```
